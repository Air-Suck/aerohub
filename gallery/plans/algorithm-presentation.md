# Gallery 算法展示改进约定

确认日期：2026-11-12。本文记录本轮讨论确认的设计，供后续实现与验收使用；不表示页面已经实现或算法已经通过验证。

## 目标与范围

面向开发者及准备迁移、使用算法的人，帮助读者理解算法适用场景、核心设计特色，以及它与 Aerohub 框架的结合方式。

本轮只处理 CAT-ORA、SUPER、YOPO，沿用现有页面风格。其他条目不在本轮内容调整范围内。

## 详情页顺序

1. 视频与精华介绍：SUPER / YOPO 桌面左侧主视频约 70%、右侧核心特色约 30%，关键词放在右侧文字下方；其他未迁移条目沿用原有顺序。
2. 应用与演示：左图右文紧凑卡片，桌面一页两张，超出横向分页；图像高度固定。上游方法图片在算法核心里同样卡片化。
3. 算法核心图：以从左到右的图展示算法本身的核心方法，突出各自设计特色。
4. Aerohub 项目框架：以相对规范的 Tool / Behavior / Function 三层架构图，展示能力归属、依赖和调用链路。
5. 案例区：保留位置，内容暂留空；本轮不编造案例或填入占位示例，后续再判断案例是否提供额外价值。

## 算法核心图

算法图尽可能聚焦自身核心，不要求拼出感知到执行的完整流水线。完整能力链路由下方项目架构图交代。算法未承担的感知、建图或执行职责不能画成算法自身能力；确需展示外部输入输出时，应明确其边界。

三张图统一阅读方向与视觉规则，但允许内部结构不同，不强行套用相同流水线。根据实际机制使用分支、回路和多机关系，并附简短说明解释设计特色。

以下是待源码及上游说明核实后落实的展示重点，不是已经核实的技术结论：

| 算法 | 展示重点 |
| --- | --- |
| CAT-ORA | 多机目标分配、协同规划及其关系；明确算法自身承担的职责，不能将外部感知纳入算法核心。 |
| SUPER | 传统模块化设计，以及备选方案、重规划机制的具体组织方式。 |
| YOPO | 学习承担或替代的处理部分，以及它与其余算法步骤的关系。 |

实现时应依据锁定源码和上游说明确定节点、连线及术语，避免将讨论中的概括直接当成技术事实。

## Aerohub 三层框架

该部分回答：算法提供什么 Tool 能力，调用什么基础 Behavior，依赖或提供什么 Function，以及这些能力怎样衔接。未涉及的层应明确表达，不为填满三层而虚构能力。

默认视图关注三层能力与调用关系。adapter、消息转换、进程拆分等实现细节保留在折叠技术说明中，不作为主要展示内容。三层图应比算法核心图更规范，便于跨条目理解。

案例不作为本轮页面叙事主线。算法特色和框架结合通过各自图文说明及明确的能力对应关系衔接。

## 验收依据

- SUPER / YOPO 的视频右侧呈现场景、核心特色与关键词，应用素材紧凑排列；关键词不得在换布局时遗漏。
- 读者能通过概述和核心图说清三个算法各自的设计特色及职责边界。
- 算法图突出自身机制；项目架构图交代三层能力与调用链路，两者分工清楚。
- 框架默认视图无需阅读进程或适配实现细节即可理解。
- 案例位置保留、内容留空，不将缺失内容包装成已有案例。
- 算法原有能力、项目已接入能力、实际验证结果分别表述，不将上游视频或代码接入当作复现成功证据。
