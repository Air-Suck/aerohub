## 1. 原生能力与复用原则

<a id="part-1-为什么以原生插件为接入基础"></a>

### 1.1 Planner：通过扩展 Behavior 适配

当前 CAT-ORA 和 Swarm-Formation 保持各自的算法实现，Adapter 将算法输出转换为 Behavior 执行请求。为承接时间化多机轨迹，本项目扩展原生 FollowPath，增加 FollowTimedPath 入口，并保留原生功能。

调用链为：Planner 算法 → Adapter 与机群调用协调 → 扩展的 FollowPath Behavior → AS2 运动参考与下层执行。Planner 代码保存在 `src/tool/navigation/planner/`，执行扩展保存在 `src/behavior/follow_path/`；算法本身不搬进 Behavior。

<a id="part-1-插件功能"></a>
<a id="part-1-复现扩展"></a>

### 1.2 Behavior：现有能力不足时按原生约定新增

先检查现有 Behavior 能否满足功能需求；无法满足时，考虑按照原生 AS2 约定创建新 Behavior。新 Behavior 使用 `as2_behavior::BehaviorServer<ActionT>` 等原生扩展接口，提供 Goal、Feedback、Result、取消及相应执行生命周期。

实现保存在 `src/behavior/<行为名>/` 的独立 ROS 2 包中，并遵循官方 [Writing a New Behavior](https://aerostack2.github.io/_09_development/_tutorials/_tutorials/behavior.html)。现有 FollowPath 时间化扩展继续保留；新增执行能力须明确时间、更新、完成与失败语义。

<a id="part-1-实现位置"></a>

### 1.3 State Estimator：按原生插件方式适配

状态估计接入遵循原生 `as2_state_estimator` 插件机制。优先复用满足需求的现有插件；需要新适配时，继承锁定版本的 `StateEstimatorBase`，通过 `PLUGINLIB_EXPORT_CLASS`、插件描述文件和包导出机制注册，由 AS2 State Estimator 宿主加载。

插件输入由算法决定，不限于原始 IMU。例如原生 `raw_odometry` 接收 `nav_msgs/Odometry`；统一输出是自身位姿、速度及 TF。外部算法可以保持独立进程，由原生插件订阅其结果并完成适配，不要求将算法本体嵌入宿主，也不要求重复进行 EKF。

适配插件保存在 `src/basic_function/state_estimator/<估计器名>/`，明确坐标、时间和发布权；地图结果交给 Perception 接口。插件不自动管理外部算法进程，也不自动具备 Behavior 的 Action 生命周期。

### 1.4 Perception：复用原生能力，再扩展或重新实现

环境感知与建图按以下顺序接入：优先复用原生 AS2 能力；无法直接复用时，考虑扩展原生功能；原生能力及扩展机制仍不适合时，再重新实现所需组件或接入外部实现。

可复用的原生组件包括：

| 组件 | 可复用功能 | 边界 |
| --- | --- | --- |
| `as2_map_server` | `scan2occ_grid` 根据激光扫描与 TF 生成二维占据地图；已有深度图／点云转激光扫描的组合启动配置 | 不等于通用三维 SLAM 或 ESDF |
| `as2_behaviors_object_perception` | 检测插件机制及 ArUco 标记检测、位姿输出 | 不代表内置所有通用检测算法；可作为 Tool 的内部实现 |

扩展或新增组件保存在 `src/basic_function/perception/<能力或算法名>/`。不限制输出为某一种地图表示，也不要求所有算法经过 Map Server；表示类型、访问接口及消费者需求必须明确。具体数据约定见第 2.5 节。

以上四类是项目的扩展职责分类，不代表它们全部采用动态插件。实现以父仓库当前锁定的 AeroHub AS2 Fork gitlink 为准；源码中存在某项能力不等于本项目已经加载或验收。

## 2. 代码目录与职责

<a id="part-2-代码目录"></a>

### 2.1 总体布局

`src/basic_function/inference/` 保存公共 ROS 接口、ROS Adapter、内部 FastAPI runtime 及 `models/<模型>/` 推理适配与独立 uv 环境。算法上游按其功能保留原目录，其他 Function 依赖 Inference 不改变自身源码归属。新增模型优先复用 runtime 与 HTTP 客户端，按真实输入输出增加模型 schema、ROS 类型及转换，不将首个模型的专有状态结构当成所有模型的通用接口。依赖锁、启动及验证说明见 [Inference](../src/basic_function/inference/README.md)。

仓库根目录的 `cards/` 统一保存能力卡片，按任务工具、规划、行为执行、状态估计、环境感知等能力类型分类，不仅保存 Tool 卡片。卡片通过组件标识关联部署组件；一个组件提供多个能力时，分别描述各能力，并声明共享进程、依赖及启停约束。组件清单描述安装与运行要求，能力卡片描述能力的选择和使用方式。

Inference 的使用者与开发者准备条件统一从 [Inference 前置条件](../src/basic_function/inference/README.md#开始前准备什么)进入。
运行已有服务、部署模型和迁移模型按对应任务准备依赖；调用方不承担模型转换环境。

- CUDA 模型的 README/setup、独立 uv 环境与权重准备按 [model-migration-cuda](../skill/model-migration-cuda/SKILL.md) 执行。
- ONNX → HMM、TCIM 绑定与 RoboPi 服务准备按 [model-migration-houmo](../skill/model-migration-houmo/SKILL.md) 执行；基础工具为固定镜像与 OHOS SDK，目标开发资源按阶段复用。
- 同一模型跨后端共用 CPU 前后处理和请求逻辑。后端只负责模型加载、张量契约、设备执行和释放，遵循[后端契约](../src/basic_function/inference/runtime/aerohub_inference/backends/README.md)。

模型 README 维护该模型的具体文件、依赖和命令；Skill 维护通用适配流程；本指导只维护职责与入口。

自建代码先按 Tool、Basic Function、Behavior 放进 `src/` 下的类型目录，再按能力与对象分目录。同一类对象的第一层子目录名称和职责相同。目录名不是 ROS 包名：`ros2 run` 仍使用包名，例如 `uav_planner_framework`、`uav_follow_path_execution`。

这些包留在本仓库，不移进锁定的 `as2/`。AS2 在自己的工作空间编译；本仓库包在 `/opt/uav_planner_ws` 编译。运行时由启动文件选择节点，或由宿主的 `plugin_name` 选中已安装的插件。

```text
src/
├── tool/
│   └── navigation/
│       ├── planner/        # 各算法的 upstream、ros2_adapter、ros1_proxy
│       ├── framework/      # 共用配置、校验和执行调用协调
│       └── interfaces/     # 兼容保留 uav_planner_interfaces 消息包
├── basic_function/
│   ├── inference/          # 模型适配、公共推理 runtime 与设备后端
│   ├── state_estimator/    # 自身状态估计与定位接入
│   └── perception/         # 环境感知、建图及环境表示
└── behavior/
    ├── follow_path/        # 时间化轨迹执行
    ├── follow_reference/   # 外部控制流执行
    └── legacy_setpoint/    # 显式启用的历史执行后端
```

完整迁移对应关系、现有外部工作区的处理及目标检测分支的接入约定见 [源码目录说明](../src/README.md)。共享接口包仍同时包含规划协议与 FollowTimedPath 执行协议；本次保留包名和类型，不因目录归类拆分 ROS 接口。Behavior 的执行职责不因此迁入 Tool。

仓库根目录的 `skill/` 用于保存复现过程中总结出来的 Skill，沉淀可复用的环境准备、构建、适配、验证和问题排查方法。按主题组织，说明适用条件、操作步骤、验证方式及已知限制，供后续复现和 Agent 使用。原始运行日志与测试产物仍放在 `log/`。

平台传感器接入使用 [平台传感器适配 Skill](../skill/uav-platform-sensor-adaptation/SKILL.md)，当前后端为 AirSim + PX4 SITL。它负责数据源选择、传感器模型、标定、时间与坐标语义及算法输入兼容；ROS 适配 Skill 负责版本与传输实现，验证 Skill 负责完整消费链和任务效果。状态估计和感知均可直接消费传感器，Tool/Planner 也可读取标准接口；应集中封装平台 SDK/RPC 差异，而非强制所有数据经过感知或 Behavior。平台采集桥、算法输入 Adapter 和算法本身应明确分工。

后续复现工作的过程文档统一写入 `skill/temp/<复现对象或任务>/`，在工作过程中持续更新，记录环境与源码版本、操作步骤、问题与解决过程、验证结果及待办，并引用 `log/` 中的证据路径。复现结束后，从这些记录中提炼经验证的可复用方法，整理成 `skill/` 下的正式 Skill；区分失败尝试、待验证方案与已验证步骤。复现过程记录不再放入 `docs/local/`，该目录仍可保存其他本地调研资料。

### 2.2 Planner

当前两个 Planner 通过扩展 FollowPath Behavior 完成执行适配。算法留在 `upstream/`，`ros2_adapter/` 适配规划结果，框架负责 Behavior 执行调用。源码归入 Navigation Tool；这不表示已经补齐通用 Tool 生命周期、资源仲裁或 Mission 实现。起飞、降落仍调用原生 Behavior。

每个 Planner 对象都使用这三层：

| 子目录 | 放什么 |
| --- | --- |
| `upstream/` | 锁定的上游算法。CAT-ORA 和 Swarm-Formation 是 Git 子模块，内部目录保持上游原样 |
| `ros2_adapter/` | 本仓库的 ROS 2 适配包，负责参数、坐标、时间和状态转换 |
| `ros1_proxy/` | 算法进程仍在 ROS 1 时的代理。以后的 Planner 没有 ROS 1 进程时，这个目录不放可执行代理 |

CAT-ORA / Swarm ROS 2 接入在 `ros2_adapter/` 内区分 `native/`（Humble 移植包）和 `bridge/`（统一 Planner 接口包）。两者为兄弟目录，父目录不声明 ROS 包，避免 colcon 在发现父包后遗漏子包。仓库根级分类及 `upstream/`、`ros2_adapter/`、`ros1_proxy/` 职责不变；部署入口在 `deployment/<算法>_humble/`。日常开发在固定共享环境中挂载源码和外部工作区，显式加载对应 install overlay，不通过新建算法镜像固化每次源码修改。

AirSim 自身的场景配置、模拟器管理和传感器桥集中在 `simulator/airsim/`；跨 AS2、PX4 和算法的应用编排保留在 `deployment/airsim/`，板端管理工具在 `tools/robopi/`。正式 Skill 统一在 `skill/`；历史产物与过程记录分别进入忽略的 `log/`、`skill/temp/`，不能因为已有文件曾被跟踪就继续提交。

两个算法共用的 Registry、配置、轨迹校验、机群调用放在 `src/tool/navigation/framework/`。共用的 ROS 2 消息、服务和 `FollowTimedPath` Action 放在 `src/tool/navigation/interfaces/`。这些共用代码不复制进每个算法目录。

新增 Planner 时建立 `src/tool/navigation/planner/<算法名>/`，并沿用上表的三层。

### 2.3 Behavior

现有 Behavior 无法满足功能需求时，考虑按官方 [Writing a New Behavior](https://aerostack2.github.io/_09_development/_tutorials/_tutorials/behavior.html) 创建新 Behavior。每个 Behavior 一个目录，该目录是一个 ROS 2 包，使用 `as2_behavior::BehaviorServer` 等原生接口，由节点自己提供 Action。

当前的时间化执行在 `src/behavior/follow_path/`。它继承上游 `FollowPathBehavior`，保留原生 FollowPath，并增加 `follow_timed_path`。启动文件只替换 FollowPath 节点，起飞、降落和到点仍用上游行为。

`src/behavior/follow_reference/` 新增外部角速度/推力流的 FollowReference 插件，复用原 Action 与插件基类，算法保持独立。已通过编译、动态加载、真实宿主接口，以及独立AirSim/PX4短程控制闭环；默认关闭普通入口的运动输出。验证控制源与真实IPC结果分别记录：真实IPC已在PC自由XYZ模式以名义3m/s完成SUPER同起终点约238m森林，两次全新启动完整通过；旧20m定高结果仅作历史，结果见IPC自己的validation文档。执行链显式加载控制器修复overlay，不代表硬10ms期限、固件逐周期100Hz消费、RoboPi或真机通过。契约与复验入口见该目录的 [README](../src/behavior/follow_reference/README.md)。

新增 Behavior 使用和 `follow_path` 相同的包内布局：

```text
behavior/<行为名>/
├── package.xml
├── CMakeLists.txt
├── include/<包名>/
├── src/
├── launch/
└── tests/
```

`src/behavior/legacy_setpoint/` 是显式 `execution_backend:=legacy_setpoint` 时才启用的历史 setpoint 链路。它不是新 Behavior 的模板。新的运动执行按 `follow_path` 来组织。

### 2.4 状态估计

`src/basic_function/state_estimator/fast_livo2/` 包含官方算法子模块、原生适配插件、ROS 1 输出桥及测试；`src/basic_function/state_estimator/pin_slam/` 包含锁定上游、原生 Humble 实时 Adapter 和原生适配插件。新增适配在 `src/basic_function/state_estimator/<估计器名>/` 按原生 State Estimator 插件方式接入自身位姿、速度和 TF。插件须继承宿主基类、导出并注册，验证 `plugin_name` 的实际加载路径；外部算法可独立运行，由插件接收其输出。代码放在本仓库，不写入锁定的 `as2/`。适配已有里程计时不要求重新做一次 EKF。

建议对象布局如下；实际 ROS 包须提供 `package.xml` 和构建文件，不能仅靠目录或 XML 自动成为可加载插件：

```text
state_estimator/<估计器名>/
├── plugin/               # 原生 AS2 状态估计适配插件，实际实现为 ROS 包
├── config/
└── launch/
```

落代码前对照父仓库当前锁定的 AeroHub AS2 Fork gitlink 中的 `StateEstimatorBase`、`raw_odometry` 和 launch 配置，不在文档中复制易过期的 commit。主状态接口和每条 TF 变换必须有明确发布权；定位重置、时间戳和坐标变换须通知或正确衔接消费者。

### 2.5 环境感知与建图

`src/basic_function/perception/` 对应基础能力层的 Perception & Mapping，与 State Estimator 并列。目前 `fast_livo2/` 记录独立配准点云接口，`pin_slam/` 记录同一 PIN-SLAM 进程的神经点锚点接口；共享算法和输出实现位于各自的状态估计目录，不重复复制源码。按第 1.4 节先复用原生能力，再考虑扩展，必要时重新实现。新增适配或扩展按 `src/basic_function/perception/<能力或算法名>/` 组织，涵盖检测、点云处理、建图、占据图／距离场生成及地图查询等；传感器驱动自身仍是独立的数据来源。

建议每个对象按需要包含 `upstream/`（复用上游时）、`ros2_adapter/`（ROS 包）、`config/`、`launch/` 和 `tests/`。不要建立空壳算法或虚构统一地图消息。空间数据接口需说明消息类型、坐标系、采样时间、数据有效期、分辨率、覆盖范围、地图版本与重置语义；检测结果需区分二维图像位置和三维空间位置。

输入可来自传感器和状态估计；输出是环境表示，供 Tool 直接订阅或查询，不塞进 `self_localization`。从点云转换到导航所需的占据图或 ESDF 是独立处理职责，必须显式实现并验证。

不强制统一地图表示或消息类型。点云、体素、占据图、TSDF／ESDF、Mesh、语义或拓扑地图均可按算法需求提供；`OccupancyGrid` 只是原生插件的一种输出。多个表示提供者和转换组件可以并存，使用明确区分的接口。统一的是表示说明、访问方式、坐标与时间、更新和失效约定，分辨率等属性仅在适用时要求。Tool 声明所需表示，部署时检查匹配关系；不兼容时显式转换或拒绝，不能把不同表示视作等价。

FAST-LIVO2、PIN-SLAM 等联合定位建图算法保持单一算法进程、单份上游源码与构建入口。按主要职责选定源码归属，其他目录只保存各自适配层或接口说明并声明依赖，不复制算法：定位结果接入 `state_estimator`，地图结果接入 `perception`。当前部署入口分别为 `deployment/fast_livo2/` 和 `deployment/pin_slam/`，均不自动替换现有系统的定位源；切换前必须通过各自预声明的 shadow gate。

上游不兼容时，先在本项目中通过 Adapter、Bridge、插件、配置或启动层适配，保持上游源码不变。只有适配层无法解决且确实必须修改上游实现时，才使用 Fork。所有 Fork 必须作为 Git 子模块接入：`.gitmodules` 记录可访问的仓库 URL，父仓库 gitlink 锁定可获取的修改提交；不得把 Fork 源码复制进主仓库，也不得以构建补丁代替最终来源。

`as2/` 中的 AS2/Pixhawk 已以 `.gitmodules` 声明的 AeroHub Fork 为源码权威；确实必须的侵入修改及回归测试直接维护在对应 Fork，再更新主仓库 gitlink。当前 AirSim 构建不再注入等价源码补丁。`px4/`、`simulator/gazebo/` 和各算法的 `upstream/` 保留各自锁定来源。

<a id="docker-build"></a>

### 2.6 使用共享 Docker 环境编译

以下操作在 Linux 开发主机的仓库根目录执行。宿主机保存源码、外部构建工作区和验证证据；Docker 只提供项目固定的 ROS、AS2、PX4 和编译工具环境。macOS 不作为已验证的编译与仿真环境。

后续复现统一使用 **AirSim + PX4 SITL**，并复用项目已发布的两份 PC 共享运行镜像：

| 镜像 | 职责 | 说明 |
| --- | --- | --- |
| `flight_board:v0.1.0` | PX4 SITL、DDS Agent、AirSim 传感器与时钟桥 | [flight_board](../deployment/flight_board/README.md) |
| `onboard_computer:v0.1.0` | ROS 2 Humble、AS2、配套 PX4 消息和开发工具 | [onboard_computer](../deployment/onboard_computer/README.md) |

复现和验收统一运行 `flight_board:v0.1.0` 内置且已与 `onboard_computer:v0.1.0` 中 `px4_msgs` 配套验证的 PX4 SITL。仓库 `px4/` 子模块用于单独开展 PX4 源码开发，不替换复现链路中的镜像内置 PX4，也不把仓库 PX4 构建产物挂载进固定 flight-board 容器。若未来需要变更复现基线中的 PX4，应将 PX4、`px4_msgs`、DDS TypeSupport 和受影响的 AS2/Pixhawk Adapter 作为一组共享环境版本进行验证与发布，不能在单个算法复现中局部替换。

镜像按[发布说明](../deployment/releases/README.md)从 GHCR 或校验后的离线包获取；使用 GHCR 时核对 registry digest，不把它与本地 image ID 混淆。`onboard_computer_dependencies:humble-px4-1.18` 是构建期内部依赖，不是第三份日常运行环境。AirSim 场景程序由宿主运行，配置见 [AirSim 启动说明](../simulator/airsim/config/README.md)；端到端入口见 [AirSim Demos](../deployment/airsim/demos/README.md)。

当前 AirSim 源码形态是锁定的 AeroHub AS2/Pixhawk fork；onboard 与 CAT-ORA hybrid Dockerfile 直接编译 fork，不再重复应用等价补丁。fork 包含项目适配，不能称为未经修改的官方源码。旧 Gazebo 镜像走另一条构建链，插件不能未经重编译就在两套 AS2 宿主间交换。

#### 日常开发约束

1. 不为每个复现对象创建算法专用镜像、临时基础镜像或新标签，也不把算法源码和每次修改 `COPY` 进共享镜像。仅在明确的团队基础环境升级任务中，才允许重建或发布共享镜像。
2. 将当前仓库、上游算法源码和宿主外部工作区挂载到共享容器。在外部工作区中使用 `colcon` 或 `catkin` 构建，将 `build/`、`install/`、`log/` 和依赖缓存保留在宿主挂载目录。
3. 运行时先 source 镜像的 ROS/AS2 基线，再 source 本次构建的 `install/setup.bash`。仅挂载源码或重启旧容器不会使修改生效；每次验证都应记录实际加载的源码提交、共享镜像标识和 overlay 路径。
4. AS2 接口、消息或 C++ ABI 改变时，在同一 overlay 链中重编译受影响的宿主、插件、Adapter 和客户端，不得让新 AS2 加载旧二进制插件。
5. 上游工作与本项目不兼容时，优先在当前项目中增加 Adapter、Bridge、插件、配置或启动层完成适配，保持上游源码及其提交不变。只有问题确实无法在项目适配层解决、必须修改上游源码时，才 Fork 上游仓库；同时记录必须修改上游的原因、基线提交和差异。Fork 必须作为 Git 子模块接入，由 `.gitmodules` 保存可访问 URL、由父仓库 gitlink 锁定修改提交；构建直接使用该子模块，不复制 Fork 源码，不以构建补丁代替。不用新建 Docker 镜像规避代码适配；Fork、commit 和 push 仍须遵守授权规则。
6. 容器内临时修改不能代替宿主持久源码。验证证据导出到被忽略的 `log/`；不需要的一次性容器和缓存应在确认不属于其他活动任务后清理。长期运行容器必须配置 Docker 日志轮转，避免 `json-file` 无界增长。

共享镜像的基线校验可使用：

```bash
# 核对日常复现所使用的已发布共享镜像。
python3 deployment/check_images.py
docker image inspect flight_board:v0.1.0 onboard_computer:v0.1.0

# 仅用于明确的共享基础环境升级任务，不是普通算法复现步骤。
# 可选：先在本地环境中设置 DEV_PROXY_URL；不需要代理时跳过此配置。
if [ -n "${DEV_PROXY_URL:-}" ]; then
export HTTP_PROXY="$DEV_PROXY_URL"
export HTTPS_PROXY=$HTTP_PROXY
export http_proxy=$HTTP_PROXY
export https_proxy=$HTTPS_PROXY
export NO_PROXY=localhost,127.0.0.1
export no_proxy=$NO_PROXY
fi

# 初始化锁定依赖，随后构建消息依赖和机载环境。
ONBOARD_COMPUTER_IMAGE=onboard_computer:dev \
  bash deployment/onboard_computer/build.sh
```

实际挂载目录、构建命令、启动顺序和 overlay 加载命令应由对应组件或 Demo 的 README 给出，不在本通用规约中虚构一套所有算法通用的容器命令。当前通用 onboard Compose 尚未完全接通外部工作区与 overlay 选择，实现差异见[固定镜像与源码开发](../deployment/onboard_computer/README.md#固定镜像与源码开发用户确认的目标)；未接通前应补齐外部工作区入口，不回退到按算法构建镜像。

网络与代理由开发者按环境配置，包括 Git、curl、容器和 Docker daemon/BuildKit。个人代理地址与认证信息不得写入共享仓库、日志或提交。

## 3. 接入方式与接口约定

新增规划、行为执行、状态估计或环境感知能力时，按第一节的扩展点实现，并核对项目锁定的 AS2 版本。

| 算法类型 | 实现要求 | 保存位置 |
| --- | --- | --- |
| 状态估计 | 按原生 State Estimator 插件方式适配，提供统一自身状态和 TF | `src/basic_function/state_estimator/<估计器名>/` |
| 轨迹或计划执行 | 现有 Behavior 不满足需求时，按原生 AS2 约定创建新 Behavior | `src/behavior/<行为名>/` |
| 外部规划 | 当前通过扩展 FollowPath Behavior 适配；算法输出由 Adapter 转换为执行请求 | `src/tool/navigation/planner/<算法名>/` |
| 环境感知与建图 | 优先复用原生能力，无法复用时考虑扩展原生功能，必要时重新实现 | `src/basic_function/perception/<能力或算法名>/` |

实现前阅读锁定版本的插件接口、注册方式和 launch 加载配置。官方教程：

- [新 Behavior](https://aerostack2.github.io/_09_development/_tutorials/_tutorials/behavior.html)

不能只凭 GoTo、FollowPath 等名称判断接口够用。原生 Behavior 表达不了所需的时间化轨迹、多机共同执行时间或滚动更新时，再在 AS2 扩展体系内增加执行能力。新增 Behavior 封装的是执行，算法仍留在算法包或 Planner 中。

具体目录见上文 [代码目录](#part-2-代码目录)。兼容性问题优先由当前项目中的独立适配层解决；确实必须修改上游源码时，使用可追溯的 Fork，记录上游基线、修改原因和差异，并把 Fork 作为 Git 子模块固定到明确且可获取的提交。

所有适配必须明确以下接口契约：

| 接口 | 必须说明的内容 |
| --- | --- |
| 传感器与状态 | 消息类型、单位、坐标系、测量时间与发布时延、频率、缺失或失效判定；不把经平台处理的测量默认称为芯片原始数据 |
| 地图与检测 | 空间表示、分辨率、覆盖范围、有效期、版本与重置语义；二维/三维检测的区别 |
| 运动执行 | 车辆对应关系、轨迹约束、共同时间基准、更新连续性、反馈与完成条件、取消及失败收口 |
| 发布与通信 | 无人机命名空间、话题/Action/Service、QoS、TF 发布权和时钟来源；同一权威接口避免竞争发布 |
| 进程与生命周期 | 启停、依赖就绪、健康检查、异常退出与恢复责任；ROS 节点、动态插件和 Behavior 不共享一套自动生命周期 |

多个估计器可并行计算，但统一状态接口必须有明确的来源选择或融合机制。把外部里程计接入 AS2，不会自动送入 PX4 EKF；PX4 外部里程计链路和融合配置需要单独实现与验证。

<a id="architecture-rules"></a>

## 4. 目标架构与运行约束

架构图及设计理由见 [项目简介](项目简介.md#architecture-design)。以下为目标架构的开发约束，不表示所有运行时机制已经实现。

部署与 Demo 接入同时遵循[四方部署职责](项目简介.md#deployment-roles)：任务脚本在工作站经 ROS 调用已就绪的算力板能力，仿真专有验收与正常任务接口分开。新增启动入口需列出“角色 → 设备/运行环境 → 进程/包 → 接口”的对应关系，说明就绪判据、任务调用与部署启停的边界，并注明相对目标的差异。

1. **区分任务调用与数据读取。** Tool 可直接读取传感器、自身状态、地图和检测结果，无需经 Behavior 转发。Navigation Tool 执行运动时调用基础 Behavior；Object Detection Tool 可以只返回结果。共享数据通路是逻辑接口集合，不强制新增中心转发节点。
2. **基础 Behavior 聚焦执行。** 高层复合行为不作为面向 Mission 的独立入口默认加载和暴露，保留上游源码；Tool 可按需加载并封装原生感知等可复用 Behavior。基础执行兼容扩展，保留原 Action 和执行反馈；FollowTimedPath 是 FollowPath 的扩展入口，不是串行调用的下一个任务。规划算法仍在 Tool 的算法侧。
3. **Mission 负责交互和编排。** Online Agent 接收人类目标、拆解任务、选择工具、消费反馈并处理失败。只能使用注册工具、经过校验的参数和授予的权限；请求被接受不等于动作完成。支持人工接管，不承担实时飞行保护。
4. **每个 Tool 必须有功能卡片。** 声明名称、版本、输入输出 schema、车辆范围、前置条件、所需数据及新鲜度、读写资源、反馈、超时、取消和失败语义。卡片与部署配置须版本化；卡片本身不是安全或互斥实现。
5. **资源互斥由软件强制执行。** 运行时按车辆与设备实例原子获取资源，如 `drone0.motion`、`drone0.gimbal`。导航与降落不能同时写运动资源；只读感知可并发，GPU 配额和设备模式修改另行仲裁。取消、超时或进程死亡时，先确认旧执行停止再转移控制权，防止锁释放后旧指令仍生效。限制绕过仲裁直接调用 Behavior 的入口；应急保护与人工接管有独立优先级。
6. **明确两种 Agent 的边界。** Offline Agent 检查依赖并生成适配包、配置、功能卡片和验证记录；Online Agent 使用已部署能力执行任务。不得把自动生成的外参当成真实标定，也不得因接口消息类型相同就宣称时间、坐标和轨迹语义兼容。
7. **多无人机共享部署放在 deployment/swarm/。** 机群规模与部署阶段必须由配置决定。前期 `pc_simulation` 为全部 N 个 UAV 分别启动独立 onboard-computer Docker；上板期 `hybrid_board` 才把其中一个节点替换为真实算力板，形成 N-1 个 Docker 加一个真实板端节点。集中式实现须在上板期同时验证板端 UAV 为中心和为 worker，地面站与外部计算固定在 PC。单机与多机 AirSim 均使用实时质心正上方的俯视观察视图；算法 Demo 复用共享设施，不复制硬编码拓扑。

<a id="validation"></a>

## 5. 开发与验收流程

### 统一复现平台（2026-11-09）

后续所有复现工作的仿真平台必须采用 **AirSim + PX4 SITL**：AirSim 提供场景、模拟传感器和物理仿真，PX4 SITL 提供飞控与平台状态，AS2 通过 PX4 平台适配层接入。涉及运动的任务必须经过 AS2 控制/平台与 PX4 SITL 执行，不使用 AirSim 运动 API 绕过飞控。

该要求适用于 Planner、Behavior、State Estimator 和 Perception 等全部集成工作。状态估计与感知应使用仿真传感器输入并验证真实下游消费；纯感知任务不强制飞行，但仍需在该平台验证其能力链。编译、单元测试、合成输入和数据集回放可以作为补充，不能代替此平台上的端到端验收；历史 Gazebo 测试结果仅作为历史证据。

### 复现成功判定

当前开发主机具备可用 NVIDIA GPU。算法依赖 GPU 时，真实 GPU 进程必须实际处理目标输入并产生由下游消费的输出；导入成功、CUDA 可见、CPU mock、合成算法输出或容器存活均不能替代该测试。

开始验证前根据组件声明、能力卡片和用户目标列出适用测试矩阵与门槛。只有矩阵中的构建与依赖、算法真实运行、接口与坐标时间契约、平台真实输入、下游消费、正常任务指标、故障与恢复，以及适用的有屏 AirSim + PX4 SITL 端到端场景全部执行并通过，证据包完整且对应同一源码、共享镜像和 overlay，才能写“复现成功”。真机测试仅在能力声明或交付目标要求真机时纳入成功矩阵，不用未要求的真机测试无限扩大范围。

失败、跳过、未执行、测试被安全门阻止或缺少证据时，必须写“复现未成功/未完成”，同时保留已通过层级与缺口。状态估计先通过预声明 shadow gate 才能切换权威；gate 失败不得强行进行 authority 测试，也不得事后放宽阈值或删掉该项来获得成功结论。

### 执行步骤

1. **确定复用边界。** 阅读锁定版本的消息定义、插件基类、加载配置和实现，记录原生组件能覆盖什么、缺少什么。
2. **选定适配方式。** 明确算法、Adapter、宿主与 Tool 的职责；检查依赖、ROS 版本、传感器、算力和许可证。外部算法可保持独立进程，不强制改写为动态插件。
3. **实现最小扩展。** 按第 2 节放置代码，按第 3 节定义接口；优先在当前项目中通过配置、Adapter、Bridge、插件或独立包完成适配。只有适配层无法解决且确实必须修改上游源码时，才 Fork 上游仓库，并记录上游基线、修改原因和差异；Fork 必须作为 Git 子模块锁定到可获取的修改提交。
4. **完成适用验证。** 检查构建与加载、真实算法执行、接口、时间和坐标、平台输入、下游消费、失效路径与资源冲突，并执行预先确定的适用测试矩阵。运动执行还需验证仿真闭环；实际真机交付前完成相应真机验收。多机轨迹须验证同步和滚动更新，单机到点成功不能代替。矩阵未全部通过时不得声明复现成功。
5. **记录并交付。** 在 PR 与项目说明中区分源码核查、编译、接口测试、仿真和真机结论，说明未覆盖的场景。运行产物进入忽略的 `log/`，复现过程记录进入 `skill/temp/`，其他本地调研资料进入 `docs/local/`；规约留在本文，运行方式和能力现状维护到项目简介。

源码编辑、构建和测试应明确工作区与版本；跨机器同步前必须核对差异，不能覆盖目标工作区独有修改。个人 SSH、路径和代理配置不进入共享文档。纯文档整理检查链接、章节和差异即可，不以未运行的仿真结果作验证声明。

## 6. 贡献方式

### 复现记录如何总结为 Skill

开始复现时按阶段读取并使用 `skill/` 中已有 Skill；过程持续写入忽略的 `skill/temp/<任务>/`，记录版本、命令、失败原因、修复、验证结果和证据路径。原始日志、bag、图像和构建产物放 `log/`，不是正式 Skill 的依赖文件。

复现结束后逐项回顾记录：将已验证且可重复使用的方法归入架构分析、ROS 适配、AS2 接入、构建、部署、验证或能力卡片 Skill。明确适用版本、输入输出、执行步骤、成功标准及限制；失败尝试可作为排障经验，但不得写成成功流程。必要的脚本和模板随正式 Skill 保存；修改后检查引用、运行相关验证，不只检查 Markdown 格式。没有新增经验时，也需在过程记录中说明理由。

发现已有 Skill 无法合理覆盖的独立能力时，先在对话中说明缺口、为何需要新 Skill、拟定职责和输入输出，未经用户确认不要创建新 Skill 或候选草稿。能力卡片保存在 `cards/`，按能力类型分类，不局限于 Tool。

PR 的 `deploy-lib`、`hdc-helper`、`oh-ros-build`、`ros-to-humble` 已从 `.agents/skills/` 迁入 `skill/` 并修正路径；它们与原 main 的 Skill 并存，尚未全部语义去重。优先按职责选择，重叠规则与当前项目约定不一致时记录差异并修订，不能认为目录合并就代表规约已经统一。

### 提交与评审

仓库地址是 <https://github.com/Air-Suck/aerohub>。`main` 是稳定分支，日常开发和 PR 以远程 `dev` 为集成基线与合并目标。

1. 先获取远程状态并将本地 `dev` 快进到最新 `origin/dev`，再从本地 `dev` 切出自己的主题分支，例如 `feat/<topic>`、`fix/<topic>` 或 `docs/<topic>`。不直接在 `dev` 上开发。
2. 在主题分支上修改和验证。不要提交 `log/`、`skill/temp/`、密钥、个人代理、本机绝对路径，以及与改动无关的子模块指针。
3. 开发结束后再次获取远程最新状态，先将本地 `dev` 快进同步到 `origin/dev`，再切回主题分支并将本地 `dev` merge 进当前主题分支。冲突必须在主题分支上解决；不把主题分支反向合入本地 `dev` 来规避冲突。
4. 在合入最新 `origin/dev` 后重新执行受影响的构建、接口和仿真测试，确认测试证据对应当前主题分支 HEAD。
5. 确认远程 `dev` 没有在测试期间继续前进；如有新提交，重复第 3、4 步。
6. 将主题分支 push 到远程，然后打开从该主题分支到 `Air-Suck/aerohub:dev` 的 Pull Request，不直接向 `main` 提交日常开发 PR。
7. PR 说明改动目的、影响范围、实际执行的验证及未完成项，并写明验证停在编译、接口测试、仿真还是真机。根据评审意见在同一 PR 上继续提交，已合并的历史不再改写。
