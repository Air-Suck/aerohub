## 1. 原生能力与复用原则

<a id="part-1-为什么以原生插件为接入基础"></a>

### 1.1 Planner：通过扩展 Behavior 适配

当前 CAT-ORA 和 Swarm-Formation 保持各自的算法实现，Adapter 将算法输出转换为 Behavior 执行请求。为承接时间化多机轨迹，本项目扩展原生 FollowPath，增加 FollowTimedPath 入口，并保留原生功能。

调用链为：Planner 算法 → Adapter 与机群调用协调 → 扩展的 FollowPath Behavior → AS2 运动参考与下层执行。Planner 代码保存在 `src/planner/`，执行扩展保存在 `src/behavior/follow_path/`；算法本身不搬进 Behavior。

<a id="part-1-插件功能"></a>
<a id="part-1-复现扩展"></a>

### 1.2 Behavior：现有能力不足时按原生约定新增

先检查现有 Behavior 能否满足功能需求；无法满足时，考虑按照原生 AS2 约定创建新 Behavior。新 Behavior 使用 `as2_behavior::BehaviorServer<ActionT>` 等原生扩展接口，提供 Goal、Feedback、Result、取消及相应执行生命周期。

实现保存在 `src/behavior/<行为名>/` 的独立 ROS 2 包中，并遵循官方 [Writing a New Behavior](https://aerostack2.github.io/_09_development/_tutorials/_tutorials/behavior.html)。现有 FollowPath 时间化扩展继续保留；新增执行能力须明确时间、更新、完成与失败语义。

<a id="part-1-实现位置"></a>

### 1.3 State Estimator：按原生插件方式适配

状态估计接入遵循原生 `as2_state_estimator` 插件机制。优先复用满足需求的现有插件；需要新适配时，继承锁定版本的 `StateEstimatorBase`，通过 `PLUGINLIB_EXPORT_CLASS`、插件描述文件和包导出机制注册，由 AS2 State Estimator 宿主加载。

插件输入由算法决定，不限于原始 IMU。例如原生 `raw_odometry` 接收 `nav_msgs/Odometry`；统一输出是自身位姿、速度及 TF。外部算法可以保持独立进程，由原生插件订阅其结果并完成适配，不要求将算法本体嵌入宿主，也不要求重复进行 EKF。

适配插件保存在 `src/state_estimator/<估计器名>/`，明确坐标、时间和发布权；地图结果交给 Perception 接口。插件不自动管理外部算法进程，也不自动具备 Behavior 的 Action 生命周期。

### 1.4 Perception：复用原生能力，再扩展或重新实现

环境感知与建图按以下顺序接入：优先复用原生 AS2 能力；无法直接复用时，考虑扩展原生功能；原生能力及扩展机制仍不适合时，再重新实现所需组件或接入外部实现。

可复用的原生组件包括：

| 组件 | 可复用功能 | 边界 |
| --- | --- | --- |
| `as2_map_server` | `scan2occ_grid` 根据激光扫描与 TF 生成二维占据地图；已有深度图／点云转激光扫描的组合启动配置 | 不等于通用三维 SLAM 或 ESDF |
| `as2_behaviors_object_perception` | 检测插件机制及 ArUco 标记检测、位姿输出 | 不代表内置所有通用检测算法；可作为 Tool 的内部实现 |

扩展或新增组件保存在 `src/perception/<能力或算法名>/`。不限制输出为某一种地图表示，也不要求所有算法经过 Map Server；表示类型、访问接口及消费者需求必须明确。具体数据约定见第 2.5 节。

以上四类是项目的扩展职责分类，不代表它们全部采用动态插件。实现以锁定 AS2 版本 `19c397309c6a41b279e6b551818ec12605cfcecc` 为准；源码中存在某项能力不等于本项目已经加载或验收。

## 2. 代码目录与职责

<a id="part-2-代码目录"></a>

### 2.1 总体布局

仓库根目录的 `cards/` 统一保存能力卡片，按任务工具、规划、行为执行、状态估计、环境感知等能力类型分类，不仅保存 Tool 卡片。卡片通过组件标识关联部署组件；一个组件提供多个能力时，分别描述各能力，并声明共享进程、依赖及启停约束。组件清单描述安装与运行要求，能力卡片描述能力的选择和使用方式。

自建代码先按能力放进 `src/` 下的类型目录，再按对象分目录。同一类对象的第一层子目录名称和职责相同。目录名不是 ROS 包名：`ros2 run` 仍使用包名，例如 `uav_planner_framework`、`uav_follow_path_execution`。

这些包留在本仓库，不移进锁定的 `as2/`。AS2 在自己的工作空间编译；本仓库包在 `/opt/uav_planner_ws` 编译。运行时由启动文件选择节点，或由宿主的 `plugin_name` 选中已安装的插件。

```text
src/
├── planner/
│   ├── cat_ora/
│   │   ├── upstream/       # 上游算法子模块
│   │   ├── ros2_adapter/   # ROS 2 适配包
│   │   └── ros1_proxy/     # ROS 1 代理
│   ├── swarm_formation/    # 与 cat_ora 相同的三层
│   ├── framework/          # 两个算法共用的配置、校验和调用协调
│   └── interfaces/         # 两个算法共用的消息、服务和 Action
├── behavior/
│   ├── follow_path/        # 时间化轨迹执行，一个 Behavior 一个包
│   └── legacy_setpoint/    # 显式启用的历史执行后端
├── state_estimator/        # 自身状态估计与定位接入
└── perception/             # 环境感知、建图及环境表示接口；含 fast_livo2 接口说明
```

仓库根目录的 `skill/` 用于保存复现过程中总结出来的 Skill，沉淀可复用的环境准备、构建、适配、验证和问题排查方法。按主题组织，说明适用条件、操作步骤、验证方式及已知限制，供后续复现和 Agent 使用。原始运行日志与测试产物仍放在 `log/`。

平台传感器接入使用 [平台传感器适配 Skill](../skill/uav-platform-sensor-adaptation/SKILL.md)，当前后端为 AirSim + PX4 SITL。它负责数据源选择、传感器模型、标定、时间与坐标语义及算法输入兼容；ROS 适配 Skill 负责版本与传输实现，验证 Skill 负责完整消费链和任务效果。状态估计和感知均可直接消费传感器，Tool/Planner 也可读取标准接口；应集中封装平台 SDK/RPC 差异，而非强制所有数据经过感知或 Behavior。平台采集桥、算法输入 Adapter 和算法本身应明确分工。

后续复现工作的过程文档统一写入 `skill/temp/<复现对象或任务>/`，在工作过程中持续更新，记录环境与源码版本、操作步骤、问题与解决过程、验证结果及待办，并引用 `log/` 中的证据路径。复现结束后，从这些记录中提炼经验证的可复用方法，整理成 `skill/` 下的正式 Skill；区分失败尝试、待验证方案与已验证步骤。复现过程记录不再放入 `docs/local/`，该目录仍可保存其他本地调研资料。

### 2.2 Planner

当前两个 Planner 通过扩展 FollowPath Behavior 完成执行适配。算法留在 `upstream/`，`ros2_adapter/` 适配规划结果，框架负责 Behavior 执行调用。它们将作为 Navigation Tool 的算法与执行协调基础；当前不提前建立 Tool 或 Mission 的实现目录。起飞、降落仍调用原生 Behavior。

每个 Planner 对象都使用这三层：

| 子目录 | 放什么 |
| --- | --- |
| `upstream/` | 锁定的上游算法。CAT-ORA 和 Swarm-Formation 是 Git 子模块，内部目录保持上游原样 |
| `ros2_adapter/` | 本仓库的 ROS 2 适配包，负责参数、坐标、时间和状态转换 |
| `ros1_proxy/` | 算法进程仍在 ROS 1 时的代理。以后的 Planner 没有 ROS 1 进程时，这个目录不放可执行代理 |

PR 的 CAT-ORA / Swarm ROS 2 接入在 `ros2_adapter/` 内区分 `native/`（Humble 移植包）和 `bridge/`（统一 Planner 接口包）。两者为兄弟目录，父目录不声明 ROS 包，避免 colcon 在发现父包后遗漏子包。仓库根级分类及 `upstream/`、`ros2_adapter/`、`ros1_proxy/` 职责不变；部署入口在 `deployment/<算法>_humble/`。实际构建与测试路径以 Dockerfile 的显式 COPY 和包选择为准。

AirSim 自身的场景配置、模拟器管理和传感器桥集中在 `simulator/airsim/`；跨 AS2、PX4 和算法的应用编排保留在 `deployment/airsim/`，板端管理工具在 `tools/robopi/`。正式 Skill 统一在 `skill/`；历史产物与过程记录分别进入忽略的 `log/`、`skill/temp/`，不能因为已有文件曾被跟踪就继续提交。

两个算法共用的 Registry、配置、轨迹校验、机群调用放在 `src/planner/framework/`。共用的 ROS 2 消息、服务和 `FollowTimedPath` Action 放在 `src/planner/interfaces/`。这些共用代码不复制进每个算法目录。

新增 Planner 时建立 `src/planner/<算法名>/`，并沿用上表的三层。

### 2.3 Behavior

现有 Behavior 无法满足功能需求时，考虑按官方 [Writing a New Behavior](https://aerostack2.github.io/_09_development/_tutorials/_tutorials/behavior.html) 创建新 Behavior。每个 Behavior 一个目录，该目录是一个 ROS 2 包，使用 `as2_behavior::BehaviorServer` 等原生接口，由节点自己提供 Action。

当前的时间化执行在 `src/behavior/follow_path/`。它继承上游 `FollowPathBehavior`，保留原生 FollowPath，并增加 `follow_timed_path`。启动文件只替换 FollowPath 节点，起飞、降落和到点仍用上游行为。

新增 Behavior 使用和 `follow_path` 相同的包内布局：

```text
behavior/<行为名>/
├── package.xml
├── CMakeLists.txt
├── include/<包名>/
├── src/
├── launch/
└── tests/
```

`src/behavior/legacy_setpoint/` 是显式 `execution_backend:=legacy_setpoint` 时才启用的历史 setpoint 链路。它不是新 Behavior 的模板。新的运动执行按 `follow_path` 来组织。

### 2.4 状态估计

`src/state_estimator/fast_livo2/` 已包含官方算法子模块、原生适配插件、ROS 1 输出桥及测试。新增适配在 `src/state_estimator/<估计器名>/` 按原生 State Estimator 插件方式接入自身位姿、速度和 TF。插件须继承宿主基类、导出并注册，验证 `plugin_name` 的实际加载路径；外部算法可独立运行，由插件接收其输出。代码放在本仓库，不写入锁定的 `as2/`。适配已有里程计时不要求重新做一次 EKF。

建议对象布局如下；实际 ROS 包须提供 `package.xml` 和构建文件，不能仅靠目录或 XML 自动成为可加载插件：

```text
state_estimator/<估计器名>/
├── plugin/               # 原生 AS2 状态估计适配插件，实际实现为 ROS 包
├── config/
└── launch/
```

落代码前对照锁定版本 `19c397309c6a41b279e6b551818ec12605cfcecc` 的 `StateEstimatorBase`、`raw_odometry` 和 launch 配置。主状态接口和每条 TF 变换必须有明确发布权；定位重置、时间戳和坐标变换须通知或正确衔接消费者。

### 2.5 环境感知与建图

`src/perception/` 对应基础能力层的 Perception & Mapping，与 State Estimator 并列。目前 `fast_livo2/` 记录已接入的独立配准点云接口；共享输出桥位于该算法的状态估计目录，不重复复制源码。按第 1.4 节先复用原生能力，再考虑扩展，必要时重新实现。新增适配或扩展按 `src/perception/<能力或算法名>/` 组织，涵盖检测、点云处理、建图、占据图／距离场生成及地图查询等；传感器驱动自身仍是独立的数据来源。

建议每个对象按需要包含 `upstream/`（复用上游时）、`ros2_adapter/`（ROS 包）、`config/`、`launch/` 和 `tests/`。不要建立空壳算法或虚构统一地图消息。空间数据接口需说明消息类型、坐标系、采样时间、数据有效期、分辨率、覆盖范围、地图版本与重置语义；检测结果需区分二维图像位置和三维空间位置。

输入可来自传感器和状态估计；输出是环境表示，供 Tool 直接订阅或查询，不塞进 `self_localization`。从点云转换到导航所需的占据图或 ESDF 是独立处理职责，必须显式实现并验证。

不强制统一地图表示或消息类型。点云、体素、占据图、TSDF／ESDF、Mesh、语义或拓扑地图均可按算法需求提供；`OccupancyGrid` 只是原生插件的一种输出。多个表示提供者和转换组件可以并存，使用明确区分的接口。统一的是表示说明、访问方式、坐标与时间、更新和失效约定，分辨率等属性仅在适用时要求。Tool 声明所需表示，部署时检查匹配关系；不兼容时显式转换或拒绝，不能把不同表示视作等价。

FAST-LIVO2 等联合定位建图算法保持单一算法进程、单份上游源码与构建入口。按主要职责选定源码归属，其他目录只保存各自适配层或接口说明并声明依赖，不复制算法：定位结果接入 `state_estimator`，地图结果接入 `perception`。当前 FAST-LIVO2 的部署与测试入口为 `deployment/fast_livo2/`，不自动替换现有多机系统的定位源。

`as2/`、`px4/`、`simulator/gazebo/` 和各 Planner 的 `upstream/` 是锁定上游。需要改上游行为时，补丁放在 `deployment/platform/patches/`，由构建过程应用。

### 2.6 使用 Docker 编译

以下命令在 Linux 开发主机的仓库根目录执行。宿主机保存源码并运行 Docker；ROS、编译工具链和算法依赖由镜像提供，不要求在宿主机安装 ROS。macOS 不作为已验证的编译与仿真环境。

网络与代理由开发者按环境配置，包括 Git、curl、Docker 构建阶段和场景资源下载。需要代理时，执行前检查代理端口和实际传输；不要把网络问题误判为源码或构建问题。个人代理地址与认证信息不得写入共享仓库、日志或提交。

后续复现统一使用 **AirSim + PX4 SITL**。AirSim 场景与传感器配置见 [AirSim 启动说明](../simulator/airsim/config/README.md)，PX4 仿真环境见 [flight_board](../deployment/flight_board/README.md)，AS2 编译环境见 [onboard_computer](../deployment/onboard_computer/README.md)，端到端入口见 [AirSim Demos](../deployment/airsim/demos/README.md)。运行前核实场景资源、渲染环境、镜像和传感器条件；缺少条件时记录未完成项，不切换到其他仿真后端替代验收。

下文基于 `deployment/platform/`、`deployment/integration/` 的构建命令和产物位置保留用于维护原有 ROS 1 / Gazebo 链路，不是后续复现的平台选择。复用其中算法包时，应接入上述 AirSim + PX4 SITL 环境重新验证。

#### AirSim / PX4 的 Docker 环境（后续复现入口）

| 环境 | 作用 | 入口 |
| --- | --- | --- |
| `flight_board:v0.1.0` | PX4 SITL、DDS Agent、AirSim 传感器与时钟桥 | `deployment/flight_board/` |
| `onboard_computer_dependencies:humble-px4-1.18` | ROS 2 Humble 与锁定的 PX4 消息及布局覆盖 | `deployment/onboard_computer/px4_msgs/Dockerfile` |
| 自建 `onboard_computer:dev` | AS2、Pixhawk 适配、导航输入和 FollowPath 扩展 | `deployment/onboard_computer/build.sh` |
| 算法应用镜像 | 在机载环境上加入算法、Adapter 和任务 | `deployment/airsim/demos/` |
| FAST-LIVO2 算法与插件镜像 | Noetic 算法进程及 Humble 原生状态插件 | `deployment/fast_livo2/` |

AirSim 场景程序由宿主运行，不包含在上述镜像中。按 [场景配置](../simulator/airsim/config/README.md) 设置被 Git 忽略的 `resources.local.yaml`；场景、计算容器与 PX4 容器通过网络连接。缺少渲染条件时明确记录验收未完成，不将离线节点检查称为飞行通过。

源码形态是官方 AS2/Pixhawk 子模块加构建补丁。AirSim 的 Dockerfile 将 `as2-airsim-pr.patch` 和 `as2-platform-px4-v1.18.patch` 应用到容器内副本；运行的是修改后的源码，不能称为未修改的原生 AS2。原子模块保持官方锁定提交。旧 Gazebo 镜像走另一条构建链，插件不能未经重编译就在两套 AS2 宿主间交换。

**准备与编译：** 以下在开发主机的仓库根目录运行。

```bash
# 可选：先在本地环境中设置 DEV_PROXY_URL；不需要代理时跳过此配置。
if [ -n "${DEV_PROXY_URL:-}" ]; then
export HTTP_PROXY="$DEV_PROXY_URL"
export HTTPS_PROXY=$HTTP_PROXY
export http_proxy=$HTTP_PROXY
export https_proxy=$HTTPS_PROXY
export NO_PROXY=localhost,127.0.0.1
export no_proxy=$NO_PROXY
fi

# 初始化锁定依赖，随后构建消息依赖和机载环境。
MIGRATION_ONBOARD_IMAGE=onboard_computer:dev \
  bash deployment/onboard_computer/build.sh
```

该脚本使用 host 网络并传入代理构建参数。`docker pull` 和 Dockerfile 的 `FROM` 由 Docker daemon/BuildKit 拉取，终端代理变量不保证对它们生效，须检查对应代理配置；不得静默回退直连。普通桥接容器内的 `127.0.0.1` 指容器自身，不能盲目复制宿主代理地址。

`flight_board` 可按 [运行镜像发布说明](../deployment/releases/README.md) 获取固定 GHCR 镜像或校验后的离线包。使用 GHCR 时核对 registry digest；不要将 registry digest 当成本地 image ID。应用 Dockerfile 中部分 `COPY --from` 固定使用 `flight_board:v0.1.0`，须按发布说明准备对应本地标签。发布版 `onboard_computer:v0.1.0` 不代表当前 main 修改已进入镜像，开发测试应重建并使用独立标签。

```bash
# 无显卡、无 PX4、无飞行指令的启动检查。
ONBOARD_COMPUTER_IMAGE=onboard_computer:dev \
  VERIFY_OUTPUT=log/airsim/onboard-dev-smoke \
  bash deployment/onboard_computer/smoke.sh

# 进入机载开发容器；源码只读挂载，构建产物仍在镜像/容器中。
docker run --rm -it --network none -v "$PWD:/workspace:ro" \
  onboard_computer:dev bash

# CAT-ORA 应用从当前开发镜像构建；构建下载显式使用代理。
docker build --network host --build-arg HTTP_PROXY --build-arg HTTPS_PROXY \
  --build-arg NO_PROXY --build-arg BASE_IMAGE=onboard_computer:dev \
  -f deployment/airsim/demos/catora_open_field/Dockerfile \
  -t uav/apps-catora-open-field:dev .
```

**运行：** 单机 Compose 是手动装配入口，不等同多机 Demo。先检查资源、车辆名、命名空间、端口、ROS domain 与 fleet 的一致性，并确认没有已有任务占用，再依次启动场景、flight_board 和机载服务：

```bash
export FLIGHT_BOARD_IMAGE=flight_board:v0.1.0
export ONBOARD_COMPUTER_IMAGE=onboard_computer:dev
docker compose -f deployment/flight_board/compose.yaml config --quiet
docker compose -f deployment/onboard_computer/compose.yaml config --quiet
bash simulator/airsim/airsim.sh check
# 以下需要可运行的图形仿真环境。
bash simulator/airsim/airsim.sh start
docker compose -f deployment/flight_board/compose.yaml up -d
docker compose -f deployment/onboard_computer/compose.yaml up -d --no-build
```

停止前先确认任务结束和降落，再分别执行上述 Compose 的 `down` 与 `bash simulator/airsim/airsim.sh stop`，只清理本次实例。多机验证使用 [各 Demo 的编排入口](../deployment/airsim/demos/README.md)，不要与上述单机实例同时占用端口。CAT-ORA PC Demo 默认是历史单点参考链；测试 FollowTimedPath 时需显式选择：

```bash
CATORA_APP_IMAGE=uav/apps-catora-open-field:dev \
  CATORA_EXECUTION_BACKEND=follow_path \
  python3 deployment/airsim/demos/catora_open_field/run.py run \
  --output log/airsim/catora-followpath-new
```

该命令会发送仿真起飞、运动和降落请求，不是离线检查。各 Demo 的实际拓扑和依赖以其当前说明为准；SUPER 的 `four-part` 使用固定工作站镜像与板端候选，旧 PC 模式仍有应用镜像依赖，不能直接认定所有 Demo 都能在纯 PC 上运行。FAST-LIVO2 见 [接入说明](../src/state_estimator/fast_livo2/README.md)，其 `Dockerfile.as2` 可用 `BASE_IMAGE` 选择当前机载镜像；算法镜像及真实传感器输入需单独准备。

机载镜像中的 AS2 位于 `/root/aerostack2_ws`，PX4 消息在 `/opt/px4_ws`，执行扩展在 `/opt/uav_execution_ws`。算法应用有自己的 overlay，例如 CAT-ORA 的 `/opt/catora_app_ws`。以上是现有快照的安装位置。日常源码修改在固定共享镜像中补编译受影响包与接口/ABI 消费者，运行时显式加载匹配的 install overlay；仅挂载源码或重启旧容器不会自动更新安装产物。通用 onboard Compose 的外部工作区接入尚待完善，当前实现差异见 [开发约定](../deployment/onboard_computer/README.md#固定镜像与源码开发用户确认的目标)。基础环境或固定快照更新单独安排。日志须导出到 `log/`。

#### 历史 ROS 1 / Gazebo 构建环境和依赖

```bash
# 在本仓库根目录执行
docker version
docker compose version
docker compose -f deployment/integration/compose.yaml config --quiet
git submodule status --recursive
```

需要能访问 Docker daemon、拉取基础镜像及安装依赖。`deployment/platform/Dockerfile` 基于 `voxelsky/ros-humble-desktop-classic:v0.0.2`，还需要 `vendor/` 中 Dockerfile 指定的依赖归档。两个 ROS 1 算法镜像分别依赖 `uav/catora:noetic-upstream` 和 `uav/swarm-formation:noetic-px4`；运行仿真还需 `uav/px4-gazebo:v1.17.0-harmonic`。

这三个 `uav/` 基础镜像不由当前 Compose 构建，须提前构建或从可用镜像来源获取；本仓库尚未提供完整的空机器引导链路。可用 `docker image inspect <镜像名>` 检查本机是否已具备。不要将 `build_from_zero.sh` 的名称理解为它能自动准备所有外部依赖。

#### 首次构建

确认子模块没有需要保留的未提交修改后，执行：

```bash
bash deployment/build_from_zero.sh
```

该脚本按顺序完成：

1. 调用 `prepare_sources.sh` 初始化递归子模块，并写入 AS2 依赖的 `.source-commit` 标记。
2. 使用 `deployment/platform/Dockerfile` 构建 `uav/aerostack2-px4:humble-v1.17`，校验版本标记、应用平台补丁并编译所选 AS2 包及依赖。
3. 执行 Compose build，构建 `runtime`、`cat-ora`、`swarm-formation` 三个服务的镜像。

基础 AS2 镜像目前仅以 `--packages-up-to` 选择平台、状态估计、运动控制和运动 Behavior；并不编译上游所有能力。后续使用 Map Server 或 Object Perception 时，须将相应包及依赖纳入镜像构建和启动配置。

#### 修改代码后的增量构建

根据改动范围选择命令，无需每次重建全部镜像：

| 修改范围 | 构建命令 |
| --- | --- |
| ROS 2 adapters、framework、interfaces 或 FollowPath 扩展 | `docker compose -f deployment/integration/compose.yaml build runtime` |
| CAT-ORA 上游或 ROS 1 代理 | `docker compose -f deployment/integration/compose.yaml build cat-ora` |
| Swarm-Formation 上游或 ROS 1 代理 | `docker compose -f deployment/integration/compose.yaml build swarm-formation` |
| AS2 依赖、平台补丁或基础镜像配置 | `bash deployment/build_from_zero.sh`，重新构建基础镜像及其下游 |

Docker 缓存会复用未变化的构建层。排查缓存问题时可使用 `docker compose -f deployment/integration/compose.yaml build --no-cache runtime`。`NO_CACHE=1 bash deployment/build_from_zero.sh` 只对平台镜像传递 `--no-cache`，不自动禁用后续 Compose 构建的缓存。

`deployment/runtime/Dockerfile` 使用明确的 `COPY` 列表。新增 `src/perception/` 或 `src/state_estimator/` 下的实际 ROS 包后，必须同时更新复制规则、依赖安装和构建/测试范围；只创建目录不会自动把包带进镜像。

#### 编译产物和源码的关系

| 内容 | 编译位置或产物位置 |
| --- | --- |
| AS2 与平台 ROS 2 包 | 镜像内 `/root/aerostack2_ws/{build,install,log}`，使用 `colcon build --symlink-install` |
| 项目 ROS 2 扩展 | 镜像内 `/opt/uav_planner_ws/{build,install,log}`，使用 `colcon build --merge-install` |
| CAT-ORA | 镜像内 `/opt/catora_ws`，使用 `catkin build` |
| Swarm-Formation | 镜像内 `/workspace`，使用 `catkin_make` |
| PX4 SITL | 仿真容器内 `/workspace/PX4-Autopilot/build`，挂载到宿主仓库 `log/px4-build/` |
| 仿真缓存与运行产物 | Compose 挂载到宿主 `log/px4-sim-cache/`、`log/px4-runtime/`、`log/resolved/` 等目录 |

通过 Dockerfile 编译的产物保存在镜像中，实际仍占用远程宿主机的 Docker 存储；不是全部写入仓库 `log/`。容器内临时修改会进入容器可写层，不能代替持久源码和可追溯的工作区编译产物。需长期保留的测试报告应导出到宿主 `log/`。

本节历史 Compose 的源码在构建时由 `COPY` 固化进镜像。即使 `as2` 服务将仓库挂载到 `/workspace`，也不代表 `/opt/uav_planner_ws/install` 自动更新。重建镜像后，已有容器仍需重新创建才会使用新镜像；单纯 `docker restart` 不会切换镜像。这些是旧快照更新机制，不是日常开发必须重建镜像的约定。日常补编译需明确挂载构建工作区并加载其 overlay；现有入口未支持时记录差异，由对应项目任务另行接入。无论选择哪种机制，运行实例切换都在任务停止、允许重启的维护窗口执行。

#### 构建验证

Runtime Dockerfile 已包含 FollowPath 扩展的 `colcon test`、`colcon test-result`，以及 framework、两个 ROS 2 adapter 和历史执行后端的 Python 单元测试。它们执行于构建阶段；命中缓存时不会重新运行。其他镜像构建成功不代表完成同等测试，更不代表多机飞行验收。

## 3. 接入方式与接口约定

新增规划、行为执行、状态估计或环境感知能力时，按第一节的扩展点实现，并核对项目锁定的 AS2 版本。

| 算法类型 | 实现要求 | 保存位置 |
| --- | --- | --- |
| 状态估计 | 按原生 State Estimator 插件方式适配，提供统一自身状态和 TF | `src/state_estimator/<估计器名>/` |
| 轨迹或计划执行 | 现有 Behavior 不满足需求时，按原生 AS2 约定创建新 Behavior | `src/behavior/<行为名>/` |
| 外部规划 | 当前通过扩展 FollowPath Behavior 适配；算法输出由 Adapter 转换为执行请求 | `src/planner/<算法名>/` |
| 环境感知与建图 | 优先复用原生能力，无法复用时考虑扩展原生功能，必要时重新实现 | `src/perception/<能力或算法名>/` |

实现前阅读锁定版本的插件接口、注册方式和 launch 加载配置。官方教程：

- [新 Behavior](https://aerostack2.github.io/_09_development/_tutorials/_tutorials/behavior.html)

不能只凭 GoTo、FollowPath 等名称判断接口够用。原生 Behavior 表达不了所需的时间化轨迹、多机共同执行时间或滚动更新时，再在 AS2 扩展体系内增加执行能力。新增 Behavior 封装的是执行，算法仍留在算法包或 Planner 中。

具体目录见上文 [代码目录](#part-2-代码目录)。兼容上游的修改放在 `deployment/platform/patches/`，由构建过程应用，不直接改写上游提交历史。

所有适配必须明确以下接口契约：

| 接口 | 必须说明的内容 |
| --- | --- |
| 传感器与状态 | 消息类型、单位、坐标系、测量时间与发布时延、频率、缺失或失效判定；不把经平台处理的测量默认称为芯片原始数据 |
| 地图与检测 | 空间表示、分辨率、覆盖范围、有效期、版本与重置语义；二维/三维检测的区别 |
| 运动执行 | 车辆对应关系、轨迹约束、共同时间基准、更新连续性、反馈与完成条件、取消及失败收口 |
| 发布与通信 | 无人机命名空间、话题/Action/Service、QoS、TF 发布权和时钟来源；同一权威接口避免竞争发布 |
| 进程与生命周期 | 启停、依赖就绪、健康检查、异常退出与恢复责任；ROS 节点、动态插件和 Behavior 不共享一套自动生命周期 |

多个估计器可并行计算，但统一状态接口必须有明确的来源选择或融合机制。把外部里程计接入 AS2，不会自动送入 PX4 EKF；PX4 外部里程计链路和融合配置需要单独实现与验证。

## 4. 目标架构与运行约束

架构图及设计理由见 [项目简介](项目简介.md#architecture-design)。以下为目标架构的开发约束，不表示所有运行时机制已经实现。

部署与 Demo 接入同时遵循[四方部署职责](项目简介.md#deployment-roles)：任务脚本在工作站经 ROS 调用已就绪的算力板能力，仿真专有验收与正常任务接口分开。新增启动入口需列出“角色 → 设备/运行环境 → 进程/包 → 接口”的对应关系，说明就绪判据、任务调用与部署启停的边界，并注明相对目标的差异。

1. **区分任务调用与数据读取。** Tool 可直接读取传感器、自身状态、地图和检测结果，无需经 Behavior 转发。Navigation Tool 执行运动时调用基础 Behavior；Object Detection Tool 可以只返回结果。共享数据通路是逻辑接口集合，不强制新增中心转发节点。
2. **基础 Behavior 聚焦执行。** 高层复合行为不作为面向 Mission 的独立入口默认加载和暴露，保留上游源码；Tool 可按需加载并封装原生感知等可复用 Behavior。基础执行兼容扩展，保留原 Action 和执行反馈；FollowTimedPath 是 FollowPath 的扩展入口，不是串行调用的下一个任务。规划算法仍在 Tool 的算法侧。
3. **Mission 负责交互和编排。** Online Agent 接收人类目标、拆解任务、选择工具、消费反馈并处理失败。只能使用注册工具、经过校验的参数和授予的权限；请求被接受不等于动作完成。支持人工接管，不承担实时飞行保护。
4. **每个 Tool 必须有功能卡片。** 声明名称、版本、输入输出 schema、车辆范围、前置条件、所需数据及新鲜度、读写资源、反馈、超时、取消和失败语义。卡片与部署配置须版本化；卡片本身不是安全或互斥实现。
5. **资源互斥由软件强制执行。** 运行时按车辆与设备实例原子获取资源，如 `drone0.motion`、`drone0.gimbal`。导航与降落不能同时写运动资源；只读感知可并发，GPU 配额和设备模式修改另行仲裁。取消、超时或进程死亡时，先确认旧执行停止再转移控制权，防止锁释放后旧指令仍生效。限制绕过仲裁直接调用 Behavior 的入口；应急保护与人工接管有独立优先级。
6. **明确两种 Agent 的边界。** Offline Agent 检查依赖并生成适配包、配置、功能卡片和验证记录；Online Agent 使用已部署能力执行任务。不得把自动生成的外参当成真实标定，也不得因接口消息类型相同就宣称时间、坐标和轨迹语义兼容。

<a id="validation"></a>

## 5. 开发与验收流程

### 统一复现平台（2026-11-09）

后续所有复现工作的仿真平台必须采用 **AirSim + PX4 SITL**：AirSim 提供场景、模拟传感器和物理仿真，PX4 SITL 提供飞控与平台状态，AS2 通过 PX4 平台适配层接入。涉及运动的任务必须经过 AS2 控制/平台与 PX4 SITL 执行，不使用 AirSim 运动 API 绕过飞控。

该要求适用于 Planner、Behavior、State Estimator 和 Perception 等全部集成工作。状态估计与感知应使用仿真传感器输入并验证真实下游消费；纯感知任务不强制飞行，但仍需在该平台验证其能力链。编译、单元测试、合成输入和数据集回放可以作为补充，不能代替此平台上的端到端验收；历史 Gazebo 测试结果仅作为历史证据。

### 执行步骤

1. **确定复用边界。** 阅读锁定版本的消息定义、插件基类、加载配置和实现，记录原生组件能覆盖什么、缺少什么。
2. **选定适配方式。** 明确算法、Adapter、宿主与 Tool 的职责；检查依赖、ROS 版本、传感器、算力和许可证。外部算法可保持独立进程，不强制改写为动态插件。
3. **实现最小扩展。** 按第 2 节放置代码，按第 3 节定义接口；优先配置或独立包。确需改上游时，保存可重放补丁并说明对应版本。
4. **按风险验证。** 检查构建与加载、接口、时间和坐标、失效路径与资源冲突。运动执行还需验证仿真闭环；实际部署前完成相应真机验收。多机轨迹须验证同步和滚动更新，单机到点成功不能代替。
5. **记录并交付。** 在 PR 与项目说明中区分源码核查、编译、接口测试、仿真和真机结论，说明未覆盖的场景。运行产物进入忽略的 `log/`，复现过程记录进入 `skill/temp/`，其他本地调研资料进入 `docs/local/`；规约留在本文，运行方式和能力现状维护到项目简介。

源码编辑、构建和测试应明确工作区与版本；跨机器同步前必须核对差异，不能覆盖目标工作区独有修改。个人 SSH、路径和代理配置不进入共享文档。纯文档整理检查链接、章节和差异即可，不以未运行的仿真结果作验证声明。

## 6. 贡献方式

### 复现记录如何总结为 Skill

开始复现时按阶段读取并使用 `skill/` 中已有 Skill；过程持续写入忽略的 `skill/temp/<任务>/`，记录版本、命令、失败原因、修复、验证结果和证据路径。原始日志、bag、图像和构建产物放 `log/`，不是正式 Skill 的依赖文件。

复现结束后逐项回顾记录：将已验证且可重复使用的方法归入架构分析、ROS 适配、AS2 接入、构建、部署、验证或能力卡片 Skill。明确适用版本、输入输出、执行步骤、成功标准及限制；失败尝试可作为排障经验，但不得写成成功流程。必要的脚本和模板随正式 Skill 保存；修改后检查引用、运行相关验证，不只检查 Markdown 格式。没有新增经验时，也需在过程记录中说明理由。

发现已有 Skill 无法合理覆盖的独立能力时，先在对话中说明缺口、为何需要新 Skill、拟定职责和输入输出，未经用户确认不要创建新 Skill 或候选草稿。能力卡片保存在 `cards/`，按能力类型分类，不局限于 Tool。

PR 的 `deploy-lib`、`hdc-helper`、`oh-ros-build`、`ros-to-humble` 已从 `.agents/skills/` 迁入 `skill/` 并修正路径；它们与原 main 的 Skill 并存，尚未全部语义去重。优先按职责选择，重叠规则与当前项目约定不一致时记录差异并修订，不能认为目录合并就代表规约已经统一。

### 提交与评审

仓库地址是 <https://github.com/Air-Suck/aerohub>，默认分支为 `main`。

1. 将仓库 Fork 到自己的账号。
2. 克隆自己的 Fork，并把 `https://github.com/Air-Suck/aerohub.git` 加为 `upstream`。
3. 从最新的 `upstream/main` 拉出主题分支。
4. 在分支上修改。不要提交 `log/`、密钥、本机绝对路径，以及与改动无关的子模块指针。
5. 推送到自己的 Fork，向 `Air-Suck/aerohub` 的 `main` 打开 Pull Request。
6. 在 PR 中说明改动目的、影响范围和验证方式，并写明验证停在编译、接口测试、仿真还是真机。
7. 根据评审意见在同一 PR 上继续提交。已经合并的提交不再改写历史。
