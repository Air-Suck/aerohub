### 概念澄清（对话中已对齐、部分已入库）

| 主题 | 要点 |
|------|------|
| 伴飞算法 vs 飞行脑 | 伴飞算法=算力板上能力模块；飞行脑=上层编排，调用伴飞算法并对接 PX4 |
| PX4 vs 高速避障 | 飞控层够用；瓶颈在伴飞感知/规划/时延 |
| Pixhawk 6C | 飞控硬件；刷 PX4（下有 NuttX）；≠算力板 |
| RoboPi+NPU | 算力板侧 |
| 硬件表拆分 | 主控 STM32/QRB/Orin vs IMU/磁/气压传感器；方案 5=QRB5165，飞控在 DSP，CPU 跑 Linux，隔离非安全级强隔离 |
| UWB | ToF 脉冲测距；视距=直线通视≠作用距离；近距遮卫星常优于差分 GNSS |
| 算法方法三分 | 传统 planner（主流）/ 学习（竞速上限对照）/ VLN（语料弱）；多机亦同，但几乎 planner 一家独大 |
| 状态估计 | 伴飞底座或飞控 EKF2，**不算**三条决策路线 |
| Flightmare | Unity+解耦动力学，偏 RL；遗留；默认 Gazebo SITL，高保真 Isaac+Pegasus |
| Pegasus | Isaac Sim 上多旋翼框架，可接 PX4 |
| 联邦架构 | 飞控域+伴飞域分治+标准协议；典型落地=飞控+伴飞 |
| Model Hub | 主要算力板内：算法×硬件适配 → 约定数据流导出（ROS 中间层 / 联邦控机出口） |
| 联邦 vs CPU+NPU | CPU+NPU 是伴飞侧异构；完整联邦还需飞控域（MCU/DSP）。联邦核心=硬实时飞控域 vs 通用 OS 伴飞域 |
| LIVO2 | FAST-LIVO2：港大 MaRS 的 LIO→LIVO 系列；主业是**激光–惯性–视觉里程计**（估自身运动），局部地图是副产品，不是独立「建图产品」 |
| FAST-LIO2 vs PX4 | 都是状态估计，但层级不同：PX4 EKF2=飞控内 IMU/GNSS/气压等；LIO/LIVO=伴飞侧稠密传感里程计，经视觉/外部位姿等接口注入 PX4，**非固件内置** |
| 为何两套估计 | EKF2 必留：姿态/角速率内环、失联回退、安全；LIO/LIVO 补 GNSS 拒止下的位姿。通常是伴飞位姿**作为量测注入 EKF2**，非两套互抢控机。高实时在飞控 IMU 环；规划用 10–几十 Hz 位姿可在伴飞 |
| 伴飞估计要什么 | 不是替代 EKF2 高速率姿态角；是无 GNSS 时给**位置/速度（及世界系位姿）**。例：竹林 GNSS 失效，IMU 姿态仍稳，但位置几秒漂米级→无 LIO 则避障规划无可信机体–障碍相对关系 |
| IMU 纯积分 | 加速度计有偏置/噪声；姿态小误差→重力投影错→假加速度；双重积分秒级米级漂。LIO/VIO 用外传感纠漂 |
| LIVO 本质（用户对齐） | GPS/GNSS 拒止时 PX4 无绝对位置锚点，IMU 航推位置漂；伴飞用激光±相机+惯性做里程计，把较准位姿喂回规划/EKF2。姿态内环仍主要靠飞控 IMU |
| GNSS | 全球导航卫星系统总称（含 GPS/北斗等）；飞控侧常用绝对位置/速度量测。密林易遮挡/多径 |
| 相对障碍 vs 机体位姿 | 单帧雷达可知「此刻相对距离」；规划要轨迹、地图融合、时间一致需要机体在局部地图中的位姿（里程计），否则多帧障碍对不齐、轨迹无稳定坐标系 |
| EGO 演进 | EGO-Planner（单机）→ EGO-Swarm（多机）→ EGO-Planner-v2（MINCO 时空优化 + 野外微集群） |
| EGO-v2 编队 | 支持编队飞与自适应变形/再成形（论文有野外编队）；横列→纵列靠上层改各机目标相对位，规划器保避障与机间安全，非整包「编队变换模式」按钮 |
| 固定编队变换开源 | 选型表原缺专用条；已补 **Swarm-Formation**（保持/穿障弹性重组）与 **CAT-ORA**（时间最优 reshape，横列↔纵列类）；语料原文有 DMPC 编队对照但未进主表 |
| 编队是否最新 | Swarm-Formation≈2022–23 仍是密林固定编队开源主力；CAT-ORA≈2025 专做 reshape。更新论文有 RE-Formation/FLIP（浙大，大尺度/韧性）但开源未稳或未见可复现主仓；未见明显「全面碾压且开源」替代 |
| 编队方法归属 | Swarm-Formation / CAT-ORA / EGO 系编队均属**传统 planner**（轨迹优化/分配），不是 RL 或 VLN |
| RACER | 主目标是**多机协同快速探索未知空间**（任务分配+轨迹）；建图/占据栅格是探索过程产物，不是测绘级建图专用系统（对比 D²SLAM 等） |
| CAT-ORA 是否最强 | 在「3D 队形 reshape + 时间最优(makespan) + 机间无碰保证」这一窄问题上自称首个完整解，相对常见 LSAP/Hungarian 平均约快 12%、极端约 49%；不是一切编队任务最强（密林保队形仍看 Swarm-Formation） |
| 列表内开源 RL 筛 | 真开源可试：**NavRL**、**MAVRL**；速度/任务均未达 ~20 m/s 丛林。Swift/MonoRace 上限对照但策略不全开源；Flying on Point Clouds 贴 LiDAR 密障但慢(~2–3 m/s)且专用仓未见稳；Sensorimotor/感知约束论文开源弱。高速丛林默认仍 SUPER |
| 开源多机 RL vs 需求 | 暂无「更贴 ~20 m/s 丛林/联邦 PX4」的开源多机 RL 可替代 planner 选型；quad-swarm-rl 及后继多为仿真/低速编队避障。多机默认仍 EGO-v2 / Swarm-Formation / CAT-ORA |
| 清华 multi-UAV-formation | IROS’25 RL：多机保队形 + 静/动态避障（OmniDrones）；开源，有实机，但仍非高速密林主选 |
| 多机 RL 开源对照 | quad-swarm-rl 与清华 formation **均开源**；另有 OmniDrones 平台、DualCL 追逃、Golden Snitch 多机竞速、ggSwarm 等，皆非 20 m/s 丛林替代 |
| 多机 RL 贴合度 | 开源多机 RL 中暂无更贴需求者；二者里清华更贴编队+避障，均撑不起 ~20 m/s 丛林，主路径仍 planner |
| 列表仿真器 | SUPER→MARSIM；EGO/GCOPTER/Swarm/EGO-v2→仓库自带的 ROS 轻量 uav_simulator/RViz（非 ROS 官方组件）；NavRL→Isaac(+Gazebo部署)；MAVRL→AvoidBench/Agilicious系；RACER→常接 MARSIM；CAT-ORA→无物理仿真器（纯数值评估+RViz 运动学回放，实飞靠 MRS UAV System；仓库 ROS1 Noetic，核心 `FormationReshaper` 类仅依赖 Eigen/mrs_lib，易抽成库移植到 ROS2）；quad-swarm-rl→自研 QuadSwarm；清华→OmniDrones/Isaac。普遍**不是** AirSim |
| 仿真分层 | 规划圈（浙大 FAST/港大 MaRS）习惯用仓库自带的轻量仿真，不走 Gazebo：简化动力学+理想控制器+点云/深度渲染，快、能跑几十架，但**不含 PX4**；RL 圈用 Isaac/Flightmare 等 GPU 并行仿真；Gazebo 主要用于 PX4 SITL 集成（MRS、NavRL 部署）。本项目建议分两层：算法在轻量仿真里开发，集成用 PX4 SITL+Gazebo（或 AirSim）闭环验证 |
| 飞控在环仿真选型 | **选 Gazebo Harmonic + PX4 SITL**（以 AAS 为骨架）。理由：PX4 官方主推且同步更新、多机开销小、原生 ROS2/uXRCE-DDS、开源可在国产 Linux 编译；AirSim 已被微软归档（2022），社区分支 Colosseum 维护弱，PX4 支持滞后，虚幻引擎吃显卡且难上国产 OS。视觉真实感不够时（反无人机视觉识别/数据生成/RL）补 **Isaac Sim + Pegasus**，不回 AirSim |
| AAS 接口 vs 算力板 | 耦合在 aircraft 容器**内容**（基础镜像 CUDA/TensorRT、YOLO 用 onnxruntime-gpu+TensorRT、DeepStream），不在接口。aircraft 容器=Docker 镜像打包的每机飞行脑参考实现（ROS2 Jazzy+感知/任务/offboard/状态共享节点+XRCE-DDS agent+Zenoh），作用：环境可复现、仿真与实机同镜像、一台电脑起 N 个即弹性扩机。算力板只需满足接口契约：点云=ROS2 PointCloud2 话题、相机=GStreamer UDP 流、飞控=uXRCE-DDS（px4_msgs）或 MAVLink、机间=Zenoh、仿真时钟 /clock。换 RK3588/昇腾/x86/国产 OS：重做镜像（换基础镜像+替换推理后端），或不用容器原生装 ROS2。**与 Model Hub 定位一致**：接口统一、板内适配由 Model Hub 负责。官方脚本/测试只覆盖 Orin；其他板除 ROS2 话题外还需：同版 ROS2（Jazzy）与 px4_msgs（与 PX4 1.17 匹配）、XRCE-DDS Agent、GStreamer 收相机流、Zenoh、IP/DRONE_ID 约定（DRONE_ID=ROS_DOMAIN_ID=MAV_SYS_ID），并改 deploy 脚本去掉 NVIDIA 运行时 |
| MPC | 模型预测控制：每周期用动力学模型预测未来一段，解带约束优化，只执行第一步再滚动。无人机里多作**轨迹跟踪控制器**，位于规划器与 PX4 内环之间，经 offboard 发角速率+推力（CTBR）或姿态+推力；PX4 自带是级联 PID 不是 MPC。常见：rpg_mpc、Agilicious、PAMPC（感知约束）、acados 求解；多机编队有 DMPC。~20 m/s 场景跟踪精度要求高时值得上。为何不直接用规划器隐含的控制量：那只是基于简化模型的**开环前馈**，真机有模型失配（质量/阻力/电池压降）、风扰、估计误差、时延，开环执行误差会累积；MPC=前馈+状态反馈+约束，每周期按实测状态重算。MPC 也可直接做规划（如 MPCC 竞速），本项目里用作跟踪 |
| AAS 覆盖面 | 不只是飞控/仿真侧：aircraft 容器就是算力板运行时（感知、任务、offboard、飞控接口、机间共享、Jetson 部署）。飞控固件原样用 PX4 不改。算力板侧"框架"强、"算法"弱（无规划器）、"硬件"窄（仅 Jetson） |
| AAS 与 ROS2 Humble | 不至于不可用：① 容器化，宿主机装 Humble 也能跑 Jazzy 容器（首选）；② 必须原生 Humble（如国产 OS/板卡 BSP 只给 Humble）则把 aircraft_ws 在 Humble 重编，px4_msgs/XRCE-DDS/Zenoh/KISS-ICP 均支持 Humble，工作量中等；③ 跨发行版（仿真端 Jazzy↔板端 Humble）DDS 互通官方不保证，常见消息多能通但需实测 |
| OpenHarmony 现状 | **Docker**：标准系统（Linux 5.10 内核）社区有跑通案例（RK3568/RK3566），但要改内核配置（cgroup/namespace/overlayfs/netfilter）+重编镜像+手动挂 cgroup，非开箱。**ROS2**：openharmony-robot 提供 OpenHarmony 版 ROS2 Humble 预编译包（含 nav2/SLAM/moveit2）；musl libc+aarch64，**板上不能原生 colcon build，必须用 ohos-robot-toolchain 交叉编译**；建议 rmw_cyclonedds_cpp。RK3588+OpenHarmony+ROS2 Humble+RKNN 已有实例（openEuler IB_Robot） |
| 框架选型（OpenHarmony 宿主） | **算力板侧选 Aerostack2**：纯 ROS2 包、支持 Humble、无需 Docker，可交叉编译上 OpenHarmony；自带 PX4 平台插件（XRCE-DDS）、起降/航点/跟踪行为、行为树任务、多机命名空间。**仿真侧**：Ubuntu 电脑跑 Gazebo Harmonic+PX4 SITL（同用 Humble，避免跨发行版）。**AAS 降为参考架构**（网络分层、HITL 接线、Zenoh、场景模型可借鉴），不直接用：依赖 Docker+Jazzy+NVIDIA，搬到 OpenHarmony 代价最大。sim-daas/dronesim 成熟度低且依赖 Docker，不选 |
| AAS 地面端 | 对应真实地面站：QGC（监控/人工接管）、mavlink-router（各机遥测分发）、ground_system（汇总各机遥测发 /tracks 全局态势）、drone_traffic_controller（集中下发 /dtc_commands，如同步编队）、Zenoh 接入机间网、视频接收。飞行不依赖它（HITL 可 GND_CONTAINER=false）。本项目多机大脑的集中式任务拆解/调度可放这一层 |
| 飞控板在环是否必要 | 基本不必要：SITL 与飞控板跑同一套 PX4 代码；真机风险在机架调参、传感器校准/振动、EKF2 外部视觉融合参数、算力板↔飞控链路（串口/网口带宽时延、时间同步）、offboard 丢失保护，HITL 本身也绕过真实传感器和电机测不到。替代：台架不装桨联调链路与模式切换 → SIH on hardware 测参数/保护逻辑 → 实飞分级（手动悬停→定点→低速 offboard→接 LIO→逐步提速）。20 m/s 场景调参最关键 |
| 仿真+独立大脑组件调研 | **首选基座：aerial-autonomy-stack（AAS）**；其次 Aerostack2（ROS2 每机 namespace/插件）、sim-daas/dronesim（Docker 每机 Controller）。无 AirSim 版成品，AirSim 需自研适配层 |
| aerial-autonomy-stack | [JacopoPan/aerial-autonomy-stack](https://github.com/JacopoPan/aerial-autonomy-stack)，ICUAS'26，约 600 星。本质是**集成发行版**（非单纯中间件）：复用 Gazebo/PX4/ROS2/Zenoh/YOLO 等，自研部分=仿真场景与带传感器机型、飞控抽象层（PX4/ArduPilot 统一成 ROS2 action）、每机参考飞行脑、网络与容器化部署、Gym 接口。三类容器：仿真（N×PX4/ArduPilot SITL+Gazebo Harmonic）、地面（QGC/mavlink-router/编队指挥）、**每机一个 aircraft 容器（=独立飞行脑：YOLO、KISS-ICP/可选 FAST-LIO 等、任务行为树、offboard 控制、ROS2 action 接口）**；同一 aircraft 镜像仿真跑 amd64、实机跑 Jetson arm64；传感数据走 SIM_SUBNET，机间走 Zenoh（AIR_SUBNET）；NUM_QUADS 弹性扩机、INSTANCE 多实例并行、可超实时、Gymnasium 接口、多 Jetson HITL。参考硬件 Pixhawk 6X+Orin NX+Mid-360。**HITL 模式=算力板在环**：Gazebo 点云/相机经 SIM_SUBNET 送到真实 Jetson，Jetson 上 aircraft 容器算出控制指令，经 UDP 发回仿真电脑上的 PX4 SITL 驱动仿真机；**真实 Pixhawk 不在环**（飞控仍是 SITL）。AAS 做不到飞控板在环：PX4 官方 HITL 只支持 Gazebo Classic（社区维护、Classic 已降级），不支持 AAS 用的 Gazebo Harmonic；SIH 可跑在飞控板上但无传感场景。若必须全链在环，需自研桥：飞控板跑 SIH 输出位姿→Gazebo 按位姿摆模型渲染传感→送算力板。务实做法：AAS 测算力板，飞控板用 SIH on hardware/台架单独测，全链靠实飞。缺口：仿真器只支持 Gazebo Harmonic（"autopilot-agnostic"指 PX4/ArduPilot 可换，不是仿真器可换）、aircraft 镜像只针对 Jetson 构建、强依赖 NVIDIA（CUDA/TensorRT/DeepStream）+Ubuntu 24.04、未内置 EGO/SUPER 类规划器、Gazebo 做 RL 训练偏慢。定位：本项目**集成层仿真与部署骨架**的首选参考 |

### 结论摘要（选型）

1. 硬件：Pixhawk 6C/6X + Orin + RealSense；≥20 m/s 加 Mid-360  
2. 飞控软件：PX4 默认；Betaflight 仅竞速对照  
3. 算法：单机高速 → SUPER；入门 → EGO；多机规划 → EGO-Swarm/v2/RACER；**固定编队** → Swarm-Formation / CAT-ORA；学习/VLN 非默认
