# 算法迁移分析

把用户给出的算法变成可审查、可实施的接入方案。分析报告与迁移实现分别标记状态。
用户只要求评估时交付报告；已要求实施时先完成必要分析，再继续已授权工作，不额外增加确认关卡。

## 1. 固定目标与证据

- 确认算法来源/版本、用户要保留的能力、当前调用方、目标运行位置与本轮交付范围。
  先查源码、清单、构建文件和现有配置；只有影响架构且无法查明的信息才询问。
- 读取当前仓库开发约定及 AS2 开发主文档；缺失时按明确 Git ref 阅读并记录提交。
  记录主仓库/子模块、工作树修改和依赖镜像，远端缓存引用不等于已核实的最新版本。
- 本项目命名与分层遵循 main；现有 AirSim/PX4 链路为权威底座。底座变更需求单列影响、依据和验证，保留原有运行组合。
- 区分源码已核查、文档声称、已有历史证据和本轮实测。关键判断引用文件位置/提交或一手来源。

完成条件：目标、版本、证据范围与尚缺输入明确；没有把未知硬件/拓扑当作既定事实。

## 2. 拆解算法与接口

沿实际执行入口追踪输入、计算、输出和调用者，区分算法核心、ROS 封装、可视化、仿真、设备驱动与任务脚本。

接口清单应包含：消息/服务/Action及端点、单位、frame/TF发布权、时钟和时间字段、频率与有效期、QoS，以及错误和重置语义。
按算法实际需要检查完整计划与当前采样点、主/备用轨迹、车辆/目标归属、导数与缺省值、地图表示和状态质量。
同名消息或能编译不能证明语义兼容；明确转换放在哪里、会丢失什么、如何验证。

依赖分为直接和间接、构建和运行、必要和可选；注明版本/ABI、来源与当前可用性。
部署到 OHOS 时另查主机代码生成工具、目标库、Python/ROS ABI 和 SDK；资源需求无实测时写待测。

完成条件：每项保留能力均能对应输入、输出、依赖和消费者；关键未核实项明确列出。

## 3. 决定 AS2 接入位置

先检查锁定版本真正提供的接口、基类、插件与加载方式，再决定复用、适配、扩展或新增。

| 职责 | 优先归属 | 应说明的接入选择 |
| --- | --- | --- |
| 路径/队形等规划 | `src/planner/<算法>/` | 核心保留；Adapter统一输出并调用基础Behavior，必要时复用公共协调逻辑 |
| 轨迹/动作执行 | `src/behavior/<行为>/` | 优先现有Behavior；不足时独立兼容扩展，明确Goal/Feedback/Result及取消 |
| 自身位姿/速度/TF | `src/state_estimator/<算法>/` | 复用或实现宿主能加载的插件；算法可为独立进程，不要求再做一次融合 |
| 环境感知/地图/表示转换 | `src/perception/<算法>/` | 按真实地图/检测接口接入实际消费者，不塞进self_localization |
| 任务顺序与用户交互 | Application/Mission | 原生起飞/降落等调用与任务恢复；Tool/Agent按当前需求，不提前实现 |
| 构建、输入转发、平台/控制器适配 | 已有运行/部署层或明确的AS2扩展点 | 先复用；若超出上述四类，单列理由并查实对应接口，不硬塞进Planner |

联合定位建图等跨职责算法可保持一份源码和一个进程，分别适配其不同输出。
Adapter可以很薄或无需独立进程；每个新增模块都应解释为何现有接口不足。

画出现有调用链与拟议架构，区分控制、状态/地图数据和部署依赖边。
每个节点标记已有/复用/新增/修改/待核实，展示实际进程/插件宿主和PC/板端位置；仅画适用的层。
随后用改动表逐一对应图中的新增/修改节点：职责、代码归属、调用方、接口、依赖、复用理由及验证。

完成条件：保留能力有明确归属，新增模块有依据，架构图、改动表与依赖关系一致。

## 4. 给出实施与验证流程表

按依赖安排阶段，每阶段列前置条件、动作、产物、通过条件、失败处理和状态。
优先用构造/接口/生命周期测试消除问题，再进入高成本场景；流程按算法类型裁剪：

1. 固定基线和算法行为对照。
2. 最小移植/适配及真实目标环境构建。
3. 包发现、类型支持、节点构造或插件实际加载；最小真实接口请求。
4. 坐标/时间/数据契约；涉及执行时覆盖更新、完成、取消、失流及正常终点模式交接。
5. 短场景/低成本闭环，再验证用户指定完整PC场景。运动算法在本项目onboard_computer环境验证，记录准确镜像。
6. 目标包含RoboPi时，先完成PC门槛，再OHOS编译/产物检查、板端接口和对应应用验证；仅PC任务标注板端不适用。
7. 交付版本、证据、回退和未通过项。

只读感知可用真实输入输出验证，不强行安排飞行；联合状态/控制消费者的闭环按其风险选取。
额外低速或简化用例需单独命名，不能替代原场景。仿真、板端加载和飞行成功分别报告。
失败时保留现场，优先最小复现；不通过放宽原任务阈值或重试筛选隐藏失败。
若同时出现明确通过和未解决失败，给出有范围的部分验证结论。

## 5. 交付与后续执行

使用 [报告模板](assets/migration-report.md)，按用户目的裁剪但保留流程、图、改动、依赖与证据。
默认落盘 `docs/migrations/<算法名>/migration.md`；已有指定文档或目的地时更新那里，原始运行产物放 `log/` 或仓库现有忽略目录。
报告完成不代表迁移就绪；未执行的门槛保持待验证，阻塞项写明最小补充信息/解除条件。

实施已获授权时，在独立分支按适配/公共修复/部署/证据组织提交；隔离每轮产物与镜像标签，避免覆盖冻结基线或用户修改。
需要ROS版本移植时读取 [ros-to-humble](../ros-to-humble/SKILL.md)；需要OHOS构建时读取
[oh-ros-build](../oh-ros-build/SKILL.md)；实际板端操作按 [deploy-lib](../deploy-lib/SKILL.md)
和 [hdc-helper](../hdc-helper/SKILL.md)执行。这些专用技能只在对应阶段需要时加载。

报告交付前核对：每个拟新增模块均在图和改动表出现；每个必要依赖都有提供方与缺失处理；
每个验收结论有对应版本、命令和结果。分析阶段尚无运行证据时，明确写未运行。
