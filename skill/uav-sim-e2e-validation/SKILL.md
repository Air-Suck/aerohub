# 仿真端到端验收与证据交付

## 拓扑与职责基线

全部 Library、算法与 Demo 遵循[四方部署职责](../../docs/项目简介.md#deployment-roles)：仿真器、飞控、算力与工作站分别标明实际设备、进程和接口，允许 PC 共置。部署层先启动能力并确认就绪，工作站任务经 ROS 调用；仿真真值评分留在仿真器/工作站侧。记录现有拓扑相对该约定的差异，不以某个 Demo 参数或单次成功代表所有项目已迁移。复用固定共享镜像，外部工作区补编译与加载步骤也应纳入运行清单。

## 先定义成功

Inference 服务验收分层记录：独立环境加载、与迁移前固定输入的候选/评分一致性、HTTP 输入和忙时语义、实际 DDS→ROS Adapter→HTTP→模型往返，再到 GPU/真实传感器与下游消费。可复用 `deployment/inference/tests/` 的公共 runtime、选择逻辑和 AS2 基准入口；模型专属 ROS smoke 在模型接入时交付。CPU 合成测试不替代 GPU 或 AirSim 验收。客户端取消测试应确认底层计算结束前不会释放 worker 的忙状态。

地面站调用 onboard 能力的通信基准先用 `deployment/inference/tests/cross_container_baseline.py`：固定地面站镜像局部生成 onboard 规范查询类型，调用实际原生 AS2 Platform 的只读 ListControlModes。按该拓扑验收 Inference 时，ROS 客户端与 Adapter 必须在不同容器中，记录两端镜像/overlay、DDS 网络与 worker 所在位置；同一 ROS 测试进程构造 Adapter 仅算合成接口证据。原生 AS2 基准通过不自动证明 Inference 通过，单宿主 Docker bridge 也不等于跨物理设备验证。

读取用户目标、组件能力、接口契约和仿真配置，运行前确定场景、链路、指标、阈值、时长及需要重复的次数。来源可以是用户要求或明确标注的工程验收建议；缺少关键指标时先明确，不能看结果后降低阈值。

输出分为通过、失败、未覆盖；缺证据不得记为通过。编译、接口测试、合成输入冒烟、真实数据回放、仿真闭环和真机验收是不同证据等级。

“复现成功”是对完整适用测试矩阵的结论，不是对某一层测试的别名。运行前建立矩阵，至少逐项判断源码与依赖构建、真实算法运行、ROS/AS2 接口、平台真实传感器输入、实际下游消费、正常场景指标、故障/恢复和资源清理是否适用；涉及运动或平台链路时纳入有屏 AirSim + PX4 SITL 闭环。只有所有适用项在同一可追溯源码/镜像版本上执行并通过，且下述证据包齐全，才能报告复现成功。

当前开发主机具备可用 NVIDIA GPU。依赖 GPU 的算法必须以真实 GPU runtime 处理目标输入并验证输出；`nvidia-smi`、CUDA 可见、库导入、镜像构建、CPU mock 或合成算法输出均不算 GPU 算法测试。不得把 GPU 项标为可选或因预计耗时而跳过。

主机 GPU 可用不等于 Docker GPU runtime 可用。验收前同时检查 NVIDIA Container Toolkit/CDI、Docker runtime 和容器内真实 CUDA 算法执行。显式挂载 `/dev/nvidia*` 与主机驱动库可用于隔离 Toolkit 缺失问题，但只属于诊断路径；除非部署清单明确支持并完成同等复验，否则不能据此宣称标准 Compose 可部署。诊断通过后仍应保留缺失前置条件和正式恢复入口。

任何失败、skip、未执行、超时无结论、证据缺失或安全门阻止都使总体结论保持“复现未成功/未完成”。可以准确报告已通过的层级，但不能用“部分成功”“基本成功”暗示完整成功。外部条件确实缺失时保留未完成状态和恢复入口；条件恢复后继续原矩阵，不事后缩小声明范围。

真机验收只在用户目标、能力声明或交付范围要求真机时纳入成功矩阵。项目统一的 AirSim + PX4 SITL 验收不是因已有 GPU 而被真机要求替代。

ROS 测试可能捕获 ImportError 后用 skipIf 跳过全部消息转换检查，最终仍显示 OK。执行接口验收前显式导入目标消息和实际 Adapter，检查通过数与跳过数；纯数学测试通过不能替代 ROS 转换测试。缺少算法应用镜像时，可在已记录版本的兼容工具链中编译当前消息与适配包、运行转换和节点构造检查，但只能报告这些包的构建及接口证据，不能声称完整算法镜像或仿真链路通过。隔离网络的构造检查也不能证明 DDS 与真实下游连通。

## 合并后全量验收的范围核对

用户要求覆盖所有集成工作或上游额外修改时，从当前源码、补丁、启动入口和两侧分支差异建立覆盖矩阵，逐项关联运行配置与证据。区分补丁中的上游版本更新和项目新增行为。源码树一致只能证明补丁重放完整，不能证明功能正确。

执行前核对入口实际选择的 backend、机数、ROS 版本和计算拓扑；Demo 名称不证明走的是 FollowTimedPath，旧单点参考与新 Behavior 链路须分别标记。需要板卡的混合部署不能直接记为 PC 仿真已覆盖。用户指定仿真后端时，不用另一个后端的历史结果替代。

首次接管被连续性检查拒绝时，对照实际状态和原生轨迹首点，优先用固定输入驱动真实算法节点复现；原生发布者可能采用 BEST_EFFORT，回归订阅需匹配。SUPER 的非占据位置曾被量化到栅格中心，产生超过执行门槛的首点偏移；应修正不必要的边界移动并验证原占据搜索仍保留，而非放宽连续性阈值。合成回归通过后再执行完整仿真。

先检查场景可执行文件、图形设备/渲染器、运行镜像和子模块是否真实可用。场景资源与镜像可能不随源码提供；下载成功不证明可启动。冻结本次源码与镜像映射，发布镜像或其他 worktree 的编译产物只能作为明确记录的依赖，不能冒充当前源码重建。

## 按能力建立完整链路

| 能力 | 必须覆盖的消费链与指标示例 |
| --- | --- |
| Planner | 场景与目标→真实规划算法→Adapter→Behavior→控制/平台→模拟运动；检查到达、约束、碰撞、多机时间协调 |
| Behavior | 实际 Goal→执行组件→控制/平台→模拟运动→完成反馈；检查跟踪、取消、更新、失败收口 |
| 状态估计 | 仿真 IMU/图像/点云→真实算法→原生插件→导航/控制实际消费→模拟运动；比较真值误差、延迟、漂移与失效行为 |
| Perception | 仿真传感器→真实算法→环境接口→实际查询/规划消费者→可观察任务结果；检查表示、覆盖及下游功能 |

真值用于评分，不得通过隐藏的真值定位源替代被验收算法。定位可先做影子运行，确认精度后再进入仿真控制闭环；影子运行不能记为闭环通过。纯感知能力不强制产生运动，但必须验证实际消费者；声称导航地图可用就需导航消费证据。

FAST-LIVO2 的合成三传感器冒烟和插件契约测试属于输入/接口级证据。只有 AirSim 实际 IMU、图像、点云进入真实算法，再由状态与感知输出被下游消费，才可记为该算法的 AirSim 闭环；AS2/PX4 的其他飞行 Demo 不能替代这条证据。

状态估计进入权威控制前必须设置 shadow gate。先让已验证的定位源控制飞行，候选估计器只输出状态并与真值比较；门限应在运行前固定。shadow 失败时，authority 场景必须记为“未执行（安全门阻止）”，不能为凑齐测试项强行切换状态源，总体复现结论也必须保持未成功。失败测试仍应完成受控降落、解除武装、证据导出和资源清理。

shadow 的精度、覆盖率和输出间隔通过后，还要核对权威 TF 每一段的更新率与控制器 freshness。低频全局定位不应直接替换高频 `odom -> base_link`；需要双速率分层时，分别测量全局校正、本地状态和 canonical 输出的唯一 stamp 频率，并执行最小 Takeoff/GoTo/Land 后再跑完整 authority 场景。门限结果用版本化脚本逐项生成 machine-readable pass/fail，不能只保存指标 JSON 后人工宣称通过。

故障测试按分层职责注入：停止全局算法时验证全局校正停止更新、本地 canonical 状态保持所需频率并完成受控降落；这不替代本地估计器故障测试。连续飞行用例之间若平台拒绝模式重置，必须按拥有关系完整重启 AirSim、PX4、桥、算法和 AS2，保留被会话残留阻止的失败尝试。

## 执行与故障恢复

1. 检查仿真传感器能否提供算法所需扫描类型、逐点时间、图像和同步标定。无法满足时记录输入不适用，不把 mock 算法或真值冒充输入补齐。
2. 隔离测试命名空间、ROS domain、端口、仿真实例和输出目录；不停止无关部署。确认权威状态、TF 和时钟源没有竞争发布。
3. 先跑正常场景，采集真实算法输出、AS2 接口、下游订阅、控制指令与运动结果，证明实际使用的是目标能力。
4. 在隔离仿真中按风险注入数据中断/延迟、算法退出、桥断连和定位重置等故障；运动组件再检查取消、停止确认和控制权交接。记录预期停止或恢复规则，重启成功不自动等于状态连续性安全。
5. 自动评估并保留失败证据。测试结束只清理本次创建的资源，确保没有残留发布者。异常恢复仍未验证时明确列出，不宣称全部成功。

PX4 SITL 与锁步 AirSim 的连接状态跨容器重启不一定自动恢复为干净初始条件。若前一轮留下 armed/offboard、异常世界更新或 TCP 会话状态，下一轮应按拥有关系受控停止并重启本轮 AirSim、PX4、桥和 AS2，再重新验证传感器、时钟、preflight 与 disarmed 状态；不能仅重启 PX4 容器后把陈旧场景状态当成新一轮证据。

## 必须交付的证据包

对测试自行启动的 ROS launch，使用独立进程组管理生命周期，容器按需启用 init 回收孤儿进程。清理须有界并检查子进程；仅 wait 启动器可能无限等待，启动器退出也不证明节点已退出。先正常中断，必要时再对本次拥有的进程组升级终止信号，保留升级记录；不能按通用进程名杀掉其他部署。将业务断言结果与清理结果分别记录，手动停止导致的非零退出不能报告为完整测试正常结束。

在 `log/<任务>/<运行标识>/` 保存：

- 运行清单：源码提交及 dirty diff、镜像 ID、场景、参数、种子、软件/硬件版本、执行命令。
- 连接证据：实际节点、插件、话题发布订阅与 TF/时钟源，证明没有旁路替代。
- 可重放记录：适用的 bag、平台日志、任务请求与反馈、真值和故障注入时间线。
- 评估报告：每个指标的预设阈值、计算方法、实测值、通过/失败、缺失数据处理；附误差曲线、轨迹或地图可视化，任务视频作为辅助而非唯一证据。
- 工件索引与校验和、复验入口、未覆盖项。报告不依赖口头描述；若数据过大，说明保留位置和获取方式。

将原始失败、定位用例和修复后结果关联到不同版本/镜像，避免后轮成功覆盖前轮失败。observe 策略下任务完成与约束满足分别判定：例如无越界观测并不代表速度上界也通过，备用标志计数也不等于独立切换次数或受控故障验收。原始日志可被忽略，精简验收摘要应受版本管理或提供固定可获取引用。

过程与证据索引写入 `skill/temp/<任务>/`。最终报告包含测试矩阵，每项注明适用性、命令/场景、证据、结果和对应源码/镜像；任何适用项未通过时不生成“成功”报告。若验收条件缺失，交付已完成层级、缺口和下一步。完成后更新有关 Skill。

## 当前经验范围

FAST-LIVO2 已完成 AirSim 1.8.1 真实 IMU/图像/LiDAR 的有屏 shadow、AS2 authority、传感器中断和算法退出矩阵。shadow 通过预设 `0.5 m` 门限后，候选状态作为唯一 AS2 状态/TF 权威完成 Takeoff/GoTo/Land；故障用例在空中真实停止容器，并以 PX4 降落、解除武装和资源清理作为通过条件。该结论不包含 PX4 外部里程计融合、真实数据集或真机。

此案例还表明，算法输出持续、点云非空和任务由另一定位源安全完成，都不能替代候选状态精度。对多模态估计器应分别记录输入消费、内部状态、shadow 精度、权威切换和故障降落；任一适用项缺失都不能声称完整闭环成功。PX4 的 `Ready for takeoff!` 日志不等于真实 preflight 通过，应订阅目标版本 `VehicleStatus.pre_flight_checks_pass` 并要求稳定窗口。AirSim lockstep 的 PX4 TCP 断开后可能使场景退出，重试必须重启本轮完整 AirSim/PX4 链，而不是只重启 PX4 容器。

PC 编排、板端执行的链路需分别记录算法镜像、目标安装 manifest、DDS 网卡与 peer、domain、PX4 system ID 及进程身份。任务退出前以停止反馈和降落解除解锁确认作为清理门槛；结果缺失或恢复未确认时保留执行端、时钟和仿真，交付其状态及恢复方法。端口占用和其他实例的存在分别检查，Docker 无法访问时不得把 inspect 失败当成资源空闲。

Fast DDS 显式 initialPeersList 用于混合部署时，应同时包含跨机 peer 和本机可达地址。仅指向远端可导致本机容器间图发现/数据缺失；白名单增加回环地址本身不能补齐 peer。先用无运动探针测量 `/clock` 的实际消息数，再进行地面数据和 TF 权威核查。2026-11-09 的 SUPER 检查中，本地 peer 探针五秒收到 251 条时钟；这只证明发现/传输修复，不等同飞行闭环通过。

多参与者发现还需保留域内 multicast discovery 或显式覆盖全部 participant 端口；只恢复 clock 参与者不能证明导航和规划节点也互相发现。地面验收要求真实 SUPER 地图输出而非仅进程存活。

混合部署共用 `/clock` 不代表 PX4 控制消息的系统时钟已同步。当前 Pixhawk 兼容补丁使用系统时钟填 PX4 控制消息时间戳，运行前沿用既有 0.5 秒墙钟偏差门槛。偏差超限时保留测量并拒绝飞行；系统对时影响设备上的其他时间敏感服务，明确获得授权后才能执行现有临时 sync-time，再做最小 Offboard 回归。2026-11-09 曾观测约 -2.77 秒偏差及 PX4 命令 176 临时拒绝；随后同一历史混合入口的 short-02 已通过，但尚无隔离变量的因果对照，不能把先后相关性写成已确认根因或持续同步可靠。

时钟异常区分初始偏差、持续频率漂移与系统服务调时造成的跳变。使用
`deployment/robopi/diagnostics/clock_probe.py` 同时记录两侧墙钟、单调时钟和 HDC
往返区间；结果中的 RTT 上下界覆盖偏差变化时，不报告确定的漂移率。墙钟/单调
时钟差只能识别跳变，不能排除共同频率校正。短观测未见跳变不等于排除间歇故障。

SUPER 混合入口现已在运行中复查既有时差门槛，超限请求任务停止与降落恢复，
保留 clock-offsets.jsonl；这属于有延迟的编排层检测，不等于控制消息级硬保护。
`test_runtime_skew_is_detected_after_initially_valid_clock` 已确认旧实现漏报、修复后
检出；该测试注入测量结果，不调整设备系统时钟，也不证明真实时钟故障下飞行恢复。
同步后的短程通过仍须与长期漂移可靠性分别报告。

### 历史全板端 SUPER 案例（兼容模式）

以下参数仅适用于 SUPER Demo，其他项目以实际入口为准。`robopi` 是 PC 规划、板端 AS2 执行；`robopi-all` 把 SUPER、导航、Adapter 和 Mission
也放在板端，PC 只运行 AirSim/PX4 与数据桥。不能据执行位置参数名称判断算法位置，
以板端安装包、Mission PID、进程树和日志为证。短程用例不替代原 forest8。

该历史拓扑偏离工作站任务边界，仅在复现旧记录时使用。其板端 Mission 读取 AirSim RPC 的碰撞状态时，检查服务监听地址，而不只检查 DDS：
原场景回环监听无法被板端访问。全板端模式绑定专用 PC 地址并在解锁前执行 RPC ping。
`AIRSIM_HOST` 也会影响现有 flight_board 中的 PX4 TCP 目标，中继监听地址必须匹配。

编排进程退出会销毁线程内 TCP relay，即使容器保留也会冻结锁步仿真。使用有独立进程
身份的中继，确认任务恢复后再清理；记录启动与停止 PID。原生 AS2 TAKING_OFF 取消
可能转入 EMERGENCY，LAND 转换不一定允许。任何应急兜底须单独记录，不能算原生
LandBehavior 通过；仿真恢复未确认而结束模拟会话也不能记为成功降落。

## 到达门槛与停止验收分开

进入目标距离门槛后，分别确认停止服务/执行反馈、控制器模式及新鲜定位下的速度保持时间；到达不能替代停止成功。YOPO 一轮已到达5 m门槛并接受8个滚动revision，但速度未在10 s内满足0.2 m/s连续1 s，仍记为失败。恢复脚本应独立尝试原生 Land，即使取消服务已返回 FAULT/失败；取消失败不能通过同一异常块跳过降落。确认 Land 结果和 disarmed 后才能清理场景/时钟。保留重复 disarm 告警，并区分主动任务通过与事后恢复成功。

原生 Land 的Action成功可能先于内部disarm清理。任务先等待平台解除武装反馈，超时后才补发disarm；already-disarmed服务拒绝必须由实际反馈判定。取消应在STOPPED状态幂等，避免任务清理触发第二次停止并与Land竞争。故障测试暂停ROSCLI包装器时需覆盖它的实际节点进程组；独立传感器容器可用pause/unpause隔离注入，保留PX4和时钟。

多轮隔离复现使用各轮独立DDS域并记录选择依据；起飞前核对clock/定位/状态发布权唯一和时钟单调。相同容器PID不是GUID冲突证据，应读实际GID；本轮探针在PID=1时得到不同GID。复现中一次未知Action/交替时钟的根因未定，保留失败，后续隔离通过不能将猜测升级为确定根因。正常/故障各轮保留独立输出目录。host与容器协作写证据时由host先创建case目录，避免root容器创建目录后host无法写注入标记，导致故障提前恢复。清理必须等待实际退出后再复用端口。

现场观看复跑可使用现有AirSim manager的`AIRSIM_RENDER_MODE=windowed`，从当前图形会话取得显示/授权配置，个人显示地址和授权路径只进本地过程记录。先核实真实场景窗口可见、地面就绪，再告知开始时间并下达任务；保留停止/Land/disarmed证据。用户要求继续查看时可保留解除武装后的窗口与空闲部署，记录本次资源身份和停止入口；现场观看未录屏时不能宣称已生成视频。

长距离任务需依据距离、配置速度与绕行余量设置独立导航等待预算，并记录CLI实际传入值；增加导航超时不改变推理/提交预算、轨迹连续性、定位新鲜度或停止门槛。速度报告区分配置速度尺度与飞行阶段测量值，用同一状态源的速度向量范数统计中位/峰值，注明时间窗口。落地后的AirSim `has_collided`可报告Landscape地形接触；保留对象、时间、法线及原始标志，分别报告飞行障碍碰撞与降落接触，不把原始true静默改为false。

## 多速率状态与有屏证据

状态估计同时包含低频全局校正与高频局部控制状态时，分别定义并测量两种 freshness：全局校正间隔反映视觉/SLAM 更新能力，高频 canonical pose、twist 和 TF 间隔决定控制可用性，不得用较宽的全局门槛替代控制门槛。频率证据使用专用轻量订阅器记录到达时间和消息时间；订阅全部高带宽话题且自身过载的采集器漏消息时，不能据此判定发布端不新鲜。

单目或其他需要运动激励的估计器不能在悬停中直接等待“就绪”后注入故障。故障场景先执行预声明的可观测运动，确认算法已进入有效跟踪且对外输出被实际消费，再写入注入就绪标记。注入后分别记录目标流停止耗时、canonical 保持期间的新样本数、从注入到降落解除武装的总恢复耗时；不能把整个降落时间误写成故障检测延迟。

有屏验收同时记录启动参数、显示环境、窗口身份和场景画面。窗口存在且未启用离屏渲染只能证明图形进程与窗口链路；桌面锁定时截到锁屏不能声称为可见场景截图，应如实保留限制并用真实传感器数据等其他证据证明该轮算法输入。
