# ProjectAirSim 场景打包

交付可启动的场景包、配置与接口说明、实际运行证据及校验和。按用户指定的场景、平台和附加模块执行；HUD、机器人客户端或其他组件仅在任务需要时纳入。

## 确定构建输入

- 从工程和本地资源配置定位 UE、uproject、ProjectAirSim 源码与依赖、目标地图及已有包。记录实际版本、工作树修改、插件源码/安装副本差异和磁盘余量；本机路径只放本地配置或 `log/`。
- 复用已确认的地图与现有工具链。需要重建 SimLibs、引擎或桥接依赖时，再查 [可复现构建](../uav-reproducible-build/SKILL.md)；普通场景打包优先增量 Build/Cook。
- 确定新输出目录、默认地图、原生 scene/robot 配置、启动机位和端口。保留旧包及已审阅地图；运行中 UE/game 进程和输出路径先核对归属。

完成条件：明确本次实际构建的地图和插件，以及运行包需要而外部环境仍须提供的依赖。

## 准备运行地图和插件

1. 编辑器中的尺寸参照、审查相机、调试对象与实际机器人分开处理。需要剔除时另存运行地图并设置 editor-only，核对审阅地图哈希未变。载具由原生 scene 创建时，确认其起点坐标、朝向和尺度，避免再带入一架静态参照。
2. UE 地图和原生 scene 是两个入口：前者提供几何与资产，后者加载机器人、传感器及控制器。UE 世界坐标、原生 NED 和 ROS frame 分别说明；按锁定版本源码核对换算。
3. HUD 的仓库源码、工程内安装副本、uproject 启用状态分别核对。把字体及许可、运行时 `.so`/`.dll` 等依赖纳入 Stage；确认经字符串动态加载的机器人网格和传感器资产也被 Cook，不能只检查地图的直接引用。
4. 保留已接受的光照。出现过期反射探针时，构建适用的反射数据；只有确认原探针对新场景不适用、且运行场景使用其他有效反射来源时，才在运行副本中排除它们。不要用隐藏屏幕提示代替处理。

已有编辑器会话可用时，在同一会话完成必要地图修改和截图。纯打包使用 UAT；插件 ABI 或新模块确需重启时再集中处理，避免每轮改图都重启编辑器。

## Build、Cook、Stage、Archive

使用工程现有打包入口。当前仓库 Blocks/HUD 的具体入口和适用限制见 [Blocks 操作参考](references/blocks.md)；其他工程据其实际目标调整，不套用走廊尺寸、地图名或机器人数量。

- 显式指定平台、构建配置、目标地图、归档目录和并发，将完整命令及日志保存到 `log/<任务>/`。按实际工程估算构建/暂存/压缩空间，不把某次空闲空间阈值当作通用要求。
- 分别判断 Build、Cook、Stage/Archive 的结果。只改资产通常无需重建未变 C++；HUD 源码/模块变化则重编译相应目标。
- 失败后复用已成功阶段。若只有 Stage/Archive 失败，输入和配置未变时用 `-skipbuild -skipcook` 续做，保持其余参数一致；避免全量清理或重建引擎。
- 编写随包启动脚本，显式加载目标地图并使用包内相对路径。原生 scene、HUD 配置及外部服务的端口应可配置。

完成条件：日志确认目标阶段成功，包内二进制、目标地图及所需动态资产和资源齐全；此时只可报告“打包成功”，尚非运行验收。

## 实际运行和故障收敛

先用打包后的二进制做短启动检查，确认 Vulkan/窗口、正确地图和所需 HUD 接口，再加载机器人做余下检查；编辑器运行成功不能替代此步骤。

启动失败时，先读第一处有效错误，使用相同配置的新旧包对照缩小范围。每次只改一个有证据的变量，并以地图加载或实际 HTTP/RPC 返回作为通过判据；GPU 枚举、进程存活均不足。遇到本轮已验证类型再读 [打包排障](references/troubleshooting.md)。同一错误再次出现且没有新证据时，停止同参数重试，保留日志并说明缺口；驱动升级、共享工具链替换或超出任务的系统修复另行处理。

按已授权范围验证：

- 正确地图及关键对象的数量、位置与姿态，运行地图中无意外尺寸参照；运行时查询使用实际对象名，不能假定编辑器 label 仍可用。
- 原生机器人加载、真实传感器/状态读取；有 HUD 时，验证实际状态、真实速度转发及计时开始/结束/重置和非法转换。观察接口不等于 planner 或飞控控制接口。
- 从实际游戏窗口获取指定尺寸的渲染截图，检查地图、HUD、字体和残留调试提示。保留一个明确的验收窗口；仅结束本任务准确匹配的测试进程。

默认完成静态运行检查。解锁、起飞、planner 运行或 PX4/ROS/AS2 闭环按用户实际任务范围执行并单独验收；SimpleFlight 静态检查不能提升为 PX4 飞行通过。

## 归档交付

完成验证后更新 manifest，写明实际构建输入、地图、启动参数、端口、外部依赖和各项通过/未执行/失败状态。附可执行启动方法和原生 scene 加载方法。

打包压缩文件前排除运行产生的 Saved/日志/缓存，保留运行必需配置与许可。生成包内文件校验清单、压缩包 SHA256，并从最终归档读取成员验证内容；原始失败日志和验证证据留在 `log/`，不伪装成产品配置。

交付直接给出包和校验文件位置、启动命令、实际运行验证结论及剩余边界。若仍有运行失败，交付可核查产物并明确未通过项，不把“构建成功”写成“可用”。

原生传感器或 SimLibs 源码变化时，先按同一 UE 工具链定向重编译与测试，确认插件
实际链接的新库，再做游戏打包；仅重 Cook 不能带入静态库改动。磁场参考配置和
原版 PX4 不解锁地面检查的已验证步骤见 Blocks 操作参考，空中地图/避障仍单独验收。
