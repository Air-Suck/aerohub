## 为什么测试阶段耗时过长

架构方案已经对齐，仍有多项未预期问题在昂贵的端到端运行中逐个暴露。耗时不能全部归因于集成本身复杂；验证程序自检、实际环境核查、启动条件及证据采集准备不充分，造成了可以避免的重复运行。执行这些验证的是助手，应由助手改进测试准备，不能把继续识别此类问题的负担交给用户。

| 实际遇到的问题 | 当时处理 | 更早发现的机会 |
| --- | --- | --- |
| 测试客户端使用保留属性名，启动异常 | 修改客户端属性 | 无仿真的节点构造检查 |
| NumPy float32 无法直接写入 JSON，运行记录中断 | 记录层显式转换为 Python 数值 | 用实际消息字段执行序列化检查 |
| 端口或 ROS domain 已被其他任务占用 | 隔离端口，增加域发现探针，仅回收本轮资源 | 启动前检查实际资源占用 |
| 固定镜像中的诊断消息与实际固件布局不一致 | 核对实际安装类型；用目标固件 uORB 获取起飞前检查，单独确认控制消息一致 | 在飞行前核对运行端消息版本，不能只看源码工作区 |
| 错误期待未解锁状态下出现 actuator 输出 | 确认原控制器和平台的输出抑制，修正地面检查预期 | 先读运行状态门控，明确地面检查能证明什么 |
| Offboard 初始化与上层模式缓存交互，导致起飞超时 | 等真实 armed/Offboard 反馈后再推进原生起飞模式切换 | 先核查状态转换顺序；动态交互仍须专门验证，不能只相信服务成功 |
| 控制源及 DDS 尚未就绪就发送目标，插件启动超时 | 增加新鲜输入、控制源与通信发现就绪门 | 启动流程先明确每个依赖的可观测就绪条件 |
| 首次成功后，发现固件内部证据采在接管前 | 将采集点放到确认实际角速度模式之后，再运行补证 | 飞行前设计证据链和采样触发条件 |

另有实际产品链路缺口：AS2 透传分支未复制推力。已用独立 overlay 补丁修复，并增加分量、时间戳及新鲜度检查。这个缺口可以通过逐字段源码核查提前发现；修复后的物理效果仍必须由真实闭环验证。

第 10 轮首次完成控制闭环，第 13 轮完成最终入口和接管后的固件证据。轮次包含启动前失败，不能当作 13 次完整飞行，也不能据此估计各类问题具体耗时；本次未做逐项耗时统计。

## 下一次 IPC 验证前的执行改进

以下是本次复盘提出的检查顺序，尚不代表已经验证了它能缩短多少时间。

1. 先自检验证程序：节点构造、实际消息字段与序列化、异常退出路径。语法检查不能代替这些运行检查。
2. 再核对实际环境：安装消息版本、overlay、端口、domain 和本轮资源所有权。失败时在飞行前停止。
3. 明确地面检查边界：观察状态和服务交互，保留未解锁输出抑制，不为测试伪造 armed/FLYING。地面通过不能证明空中模式交接正确。
4. 将启动依赖写成可观察条件：输入新鲜、DDS 发现、控制源就绪、真实飞控模式；避免仅用服务返回值或固定等待推进。
5. 飞行前列好成功、失败和恢复的证据及采样时机，尤其是接管后的固件状态和实际运动，减少成功后才补证重跑。
6. 每轮指定要消除的未知项。出现意外后先检查同类问题是否仍存在，完成必要的局部验证，再重跑完整流程。

后续接真实 IPC 时，优先复用已经通过的执行链，单独验证 IPC 的输出单位、坐标、求解健康和旧解有效期。不得把验证控制源的成功直接算作 IPC 成功，也不应在没有证据时同时更改算法、执行插件和测试阈值。

已开始迁移独立算法内核并建立固定依赖构建入口。预检查拦截了镜像缺失求解依赖、上游求解API/状态接口混用、几何库ROS1可视化依赖和C++17比较器问题，未为这些问题启动飞行。实际构建与检查范围见 [native说明](ros2_adapter/native/README.md)。完整会话接入、真实数据回放和导航绕障仍未完成；本节不替代后续验收结果。

### native滚动运行暴露的遗漏

`native-control-02`只有初始数帧有效，未完成接管，已正常降落。随后`native-ground-03`在未解锁、Behavior未激活状态，用实时输入运行当前点目标，472帧中仅4帧有效，明确暴露重复A*失败。源码对照确认：助手迁移Planner调用时遗漏了上游PathReplan末尾的Reset；已改为每次搜索前Reset，并加入20次连续重规划检查。单次路径成功检查不足以代表滚动规划，这是本轮实际遗漏，不能归因于上游。后续须通过地面持续输出复验后再飞行。forest样例仍未通过。

### 时序、动力学与模式反馈分开处理

- native-control-03/04均因墙钟看门狗退出。补齐上游裁剪/0.2m降采样后，地面仍存在150ms间隔；采样到的求解单轮约1–3ms，不能把全部间隔归为计算耗时。
- 将求解与发送解耦：只在100ms墙钟与ROS年龄内重复最近命令，不更新原命令/求解时间；失败立即缓存无效结果。native-ground-07有1715次发送、525个不同求解时刻，1688有效、27超龄无效；发送最大间隔16.8ms，有效帧最大间隔52.6ms。不是1715次求解或100Hz闭环验收。
- native-control-05倾角约0.472rad超过0.35，位置误差最大约0.080m，未通过且已降落。对齐当前姿态下的加速度状态，并改为低速样例参数：加速度1m/s²、jerk2m/s³、参考推进0.05m/0.1s，保持0.5m/s速度与原验收阈值。此为待动力学验证的修正，不宣称解决。
- native-control-06因BODY_RATES反馈缺失退出，无法据此判断上述动力学修正有效。已补反馈ready/age诊断与ControllerInfo录包，并准备未解锁模式探针。各轮均正常恢复降落，不作forest成功记录。

### forest 前控制门与真实输入诊断

`native-control-08` 使用真实 IPC 完成悬停、非零 yaw、输出中断收口与原生降落；验证控制源的历史通过不计入该结果。`native-short-05` 完成 4m 导航、取消、停止与原生降落：估计到达误差 0.0821m、真值到达误差 0.1191m、停止后真值误差 0.2021m、最大倾角 0.1322rad。它不代表森林绕障通过。

前序失败暴露两个独立问题：QP 冷启动耗时，以及硬速度约束下 jerk=2 的制动可行性。保留原安全门限，采用完整原始/对偶/rho 热启动，并预先固定低速参考0.25m/s、jerk5m/s³和硬逐轴速度0.5m/s。以失败轮真实输入离线回放确认后，再进行短程验证。评分代码的 BLAS 线程及不必要相机流也消耗仿真预算，已限制评分线程并只启用实际需要的 LiDAR；保留 GPU 渲染、真实 PX4 和传感器。

`forest-01` 初始 QP 未收敛。独立导出实际 QP：45变量、1860约束，零输入和 LP 均可行。独立 SLSQP 求得目标 -429.3376139；其中1712行走廊约束在 jerk 盒内必然满足，删除后目标一致且原约束违例为零。实现精确盒约束冗余判定，不放宽边界或接受 inaccurate 状态；新增近障碍平面保留回归。`forest-replay-04` 求解43次全部收敛，p95约5.13ms；但旧录包本身存在输入间隙，不据此宣称端到端通过。

`forest-02` 在接管后因控制流过期退出，已正常降落解除武装。MPC 虽只有几毫秒，串行 A* 重规划仍需40–72ms，不能用求解耗时替代整个控制周期预算。改为独立快照规划线程、独立栅格、同会话/地图年龄校验后安装路径，MPC继续使用当前点云构建走廊。3项核心回归及实际节点契约通过；同轮真实输入回放 `native-deps/forest-replay-05` 有效帧最大墙钟间隔12.2ms、求解p95约4.40ms。该录包的有效会话很短，仍须完整森林飞行验证。

`forest-03` 控制帧有效但 BODY_RATES 反馈处理年龄204ms退出；录包中 controller/info 持续发布，不能归因于发布者停止。新增独立模式回调组与双线程宿主后，隔离接口回归进一步复现 ACROMotion 根据第二份模式缓存重复协商，100ms等待触发墙钟保护。执行插件改为统一显式协商、确认实际反馈后发布配对 Motion Reference；不再逐帧隐式协商，不绕过 AS2 控制器。真实宿主持续执行、状态拒绝、修改、暂停/取消、断流和禁用输出回归通过，证据 `log/ipc/native-deps/mode-group-{interfaces,disabled}-02.log`。开始 `forest-04` 完整复验；上述结果仍不算完整森林通过。

`forest-04` 已稳定接管并前进约6.8m，模式反馈问题未再触发；最大倾角0.1266rad、速度模0.3028m/s，最终在障碍附近规划失去进展，随后无效控制触发保护并原生降落解除武装。`forest-replay-06` 3384次成功求解，p95约1.75ms，导出的首次失败QP包含598个NaN项；这不是OSQP性能问题。点云核查表明当前位置距障碍约0.62–0.70m，但上游立方膨胀和栅格量化仍可把起点标占据，之后持续沿旧局部路径停滞。长时间停滞后EMVP返回非有限平面，原接口的success标志不足以证明输出有效。

针对上述输入，增加有限范围起点连接：仅当原起点栅格占据时，搜索0.6m内自由格点，并以原始处理点云检查整条连接线的欧氏安全余量不低于既有SFC余量0.55m；保留真实起点并把连接线作为路径首段，不清障碍格，也不直接把位姿替换成自由格。无合法连接必须失败。EMVP和SetFSC分别拒绝非有限平面，每轮重建走廊前清空上一轮部分约束。新增真实首点保留、实际占据无连接拒绝及非有限平面拒绝回归。安全验收门限保持不变，仍需完整forest验证。

`forest-05` 已完成真实绕障，但未在180仿真秒内完成到达，仍判失败并正常降落解除武装：最近估计目标误差1.4346m、真值误差1.4017m、最大倾角0.1546rad、最大速度模0.3460m/s、最小原始点云间距0.6160m、最大横向偏离2.6380m，直线路径确有障碍且规划绕行证据成立。不能将“已经绕障”提升为完整应用通过。

下一候选仅把参考推进速度从0.25调整为0.30m/s，保留0.5m/s硬逐轴速度、0.55m走廊、jerk5、所有安全/精度/停止标准和180秒时限。此前节点用0.5倍目标速度限制参考推进，新增0.6倍限制以允许该候选；默认reference_speed仍为0.25。任务配置中的参考速度与规划余量现在实际传入只读启动参数，不再只是元数据。必须先回放和短程门验证，再进入完整森林；不追认旧轮通过。

归因补充：源码再次核对发现上游PathReplan本已有“起点占据时搜索附近点”的分支。native初期只迁移了正常路径、遗漏该分支，是本次适配覆盖不足，不能把forest-04全部归为上游缺陷。现有有限连接修正补回该意图，同时增加连接安全检查与真实首点保留；上游无界搜索与直接换起点未照搬。native README已增加运行分支对应表，明确其他有意差异和未迁移功能。关于推力时间尺度的想法尚无独立证据，本轮没有据此改动控制方程。

`native-short-06` 0.30m/s物理导航门通过（估计误差0.0518m、真值误差0.0602m、最大倾角0.1077rad、停止速度0.0825m/s）；但之后逐样本分析发现1044个PX4样本中3个无法匹配完整源帧，故不能将其作为完整下游数值验收通过。实际记录可见某帧角速度与上一帧推力组合；源码确认控制器publishCommand重写twist时间戳，而平台分别缓存twist/thrust且无配对检查。新增独立补丁分别保留BODY_RATES源时间戳、在Pixhawk发送处拒绝混序/超龄/非有限/错误坐标的样本；不放宽数值匹配误差。

`forest-06` 0.30m/s仍在首个障碍前超时，已降落解除武装。进一步对照上游LocalPcCallback/TimerCallback，初版native“单帧点云且每帧全量重规划”与上游“十帧静态历史、剩余路径受阻时才重规划”不同；参考速度不能代替此语义差异的修正。现补十帧、最多2秒的静态历史，并在独立规划线程刷新栅格后检查剩余路径；未受阻且未接近临时终点时保留路径。新增未变化路径保留及新障碍触发重规划回归。该问题属于移植运行语义覆盖不足，不能归为算法天生不适合forest。

补丁后实际平台类配对回归与真实FollowReference接口回归通过。十帧/条件重规划版本 `forest-replay-09` 成功求解3380次，A*搜索约111次（之前同段约602次）；但尾段出现不可行，最大有效帧间隔210ms，因此**整段时效门未通过**。该录包运动由旧规划控制产生，而新算法仍以新推力输出估计加速度，反事实回放的反馈状态不再与旧运动一致；这是诊断限制，不能据此认定真实新闭环一定可行或不可行。没有接受失败QP输出。后续用隔离4m水平+1m爬升门判断实际闭环，严格检查PX4完整源帧映射。回放脚本新增显式timing_gate_passed及默认失败退出，诊断性容许退化需显式--allow-degraded，不把“有成功求解”当整段通过。

### 当前处理决定：保留指标，后续优化

经本轮讨论，约192ms是求解时所用最新扫描相对原始采样时间的年龄，不是IPC计算了192ms，也不能据此断言存在200ms的IPC处理延迟。当前约10Hz新扫描及帧间复用可以解释这一年龄量级；IPC预处理和正常求解仍为几毫秒级。

该决定只适用于当前已验证范围。对于突发/动态障碍，192ms在3m/s下约对应0.576m前进，必须进入发现—规划—制动预算；已经注册的静态地图点不因此整体错位。后续对齐动态场景时，再补齐采样、RPC、发布、TF、地图安装、首次消费及实际控制响应的时间边界，并做固定源扫描率下10/40Hz启动取帧的受控对照。先保留完整证据与不确定项，不把指标年龄等同于算法响应延迟，不通过修改stamp或放宽超时掩盖。
